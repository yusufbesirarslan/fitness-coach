## Track 1 — Infra / Reliability / Structure

### A1 — HIGH (availability): heavy AI routes bypass the concurrency gate  ⟶ verified
**Files:** `app/blueprints/nutrition/meallog.py:296-299` (`/meal-log/review`),
`app/blueprints/food.py:18-21` (`/api/food/search`).

Both routes call the LLM but their decorator stack is only `@require_auth` +
`@limiter.limit(...)` — a **per-user frequency** cap, not a **global concurrency**
cap. The sibling AI routes (`coach.py:28`, `training.py:74/128`, `tracking.py:151`,
`nutrition/plan.py:76`, `menu.py:280`) all add `@ai_concurrency_gate` as the innermost
decorator; these two do not. Confirmed directly:

```
# meallog.py:296   @bp.route("/meal-log/review", methods=["POST"])
#          :297   @require_auth
#          :298   @limiter.limit(AI_RATELIMIT, ...)   ← no @ai_concurrency_gate
#          :355   raw = _openai_chat(...)             ← direct LLM call
```

`/meal-log/review` calls `_openai_chat` directly, and `_openai_chat`
(`app/services/ai.py:26-65`) does **not** acquire `model_concurrency_slot()` — only
`_heavy_chat`/`_bedrock_validate_image` do. So this route is uncapped at **both** the
route-gate and the model-semaphore level.

**Failure scenario:** 8+ users each hit `/meal-log/review` concurrently (each under
its own frequency limit). Each opens an OpenAI call (`timeout=30`, `max_retries=2` →
up to ~90s wall) holding a gunicorn thread. All 8 threads (single worker) fill;
`/health` and cheap routes queue behind them → Docker HEALTHCHECK / deploy `/health`
gate times out → **automatic rollback of a healthy deploy**, or a live outage. This is
exactly the scenario `ai_gate.py` exists to prevent.

**Fix:** add `@ai_concurrency_gate` as the innermost decorator on both routes. Also
wrap `_openai_chat` in `model_concurrency_slot()` (or route `review_meals` through
`_heavy_chat`) so no LLM path can acquire unbounded provider connections.

### A2 — MEDIUM (availability): wearables sync route not behind any concurrency gate
**File:** `app/blueprints/wearables.py:111-130` (`/api/wearables/<provider>/sync`),
`:133-150` (`/api/wearables/whoop/<resource>`).

Each call fans out multiple sequential outbound HTTPS calls to WHOOP/Google
(`app/services/wearables/adapters.py:100-169`, each `timeout=10`), so one request can
hold a thread ~30-60s. It has a per-user `SCRAPE_RATELIMIT` but **no
`@scrape_concurrency_gate`** — unlike the menu scraper (`menu.py:92`), which was given
a separate semaphore for exactly this reason. Concurrent syncs across users can consume
the thin thread reserve.
**Fix:** apply `@scrape_concurrency_gate` to the wearable sync/resource routes
(network-bound, LLM-independent — same bucket as the menu scraper).

### A3 — MEDIUM (availability): `model_concurrency_slot()` blocks with no timeout
**File:** `app/services/ai_gate.py:59` (`_model_slots.acquire()` — no timeout),
`:66-83` (`warn_if_gates_exhaust_threads`).

The boot check asserts `AI(4) + SCRAPE(2) = 6 ≤ WEB_THREADS(8) - 2`, so "2 threads
always free for `/health`." That holds only if **all** AI/network work flows through
the two route gates. It does not: the ungated routes in A1/A2 and the `model` semaphore
being a **third independent, blocking-with-no-timeout** gate all consume web threads
outside the accounting. When the 4 model slots are held, an ungated `_heavy_chat` caller
blocks forever on `.acquire()`, eating the "reserved" 2. Also `reserve = 2` equals
`THREAD_RESERVE_MIN` exactly, so any config nudge (`AI_MAX_CONCURRENCY=5`) silently
zeroes the reserve with a **warning, not a boot failure**.
**Fix:** give `model_concurrency_slot()` a bounded acquire timeout (→ fallback/503 rather
than block a thread); fold ungated AI routes into the gate (A1); consider making the
reserve check fail-fast.

### A4 — MEDIUM: pre-Alembic DB gets `stamp(head)` without `upgrade()`
**File:** `app/db_init.py:23-56,158-166`.

When `alembic_version` is absent the code **skips `upgrade()`**, runs `db.create_all()`,
then `stamp(head)`. `create_all()` creates missing *tables* but never adds missing
*columns* to tables that already exist. A legacy DB that has the tables but predates a
column-adding migration (e.g. `f1a2b3c4d5e6` freemium cols, `c4d5e6f7a8b9` language)
would be stamped fully-migrated while silently missing those columns → runtime 500s
(`column does not exist`) that no migration will ever repair, because the chain is now
marked complete. Bounded (the add-column migrations are idempotent/existence-checked, so
a fresh path is fine; risk is a partially-migrated, never-stamped legacy DB).
**Fix:** for the `not _has_alembic` branch prefer `stamp(base)` + `upgrade()` over
`stamp(head)`, or verify model columns exist before stamping head.

### A5 — LOW: `/health?deep=1` blocks a thread on a 3s outbound probe
**File:** `app/__init__.py:77-85`. Each deep check does
`requests.get(FATSECRET_BASE_URL..., timeout=3)`. Fine for the deploy gate, but a
frequent external readiness monitor blocks a web thread up to 3s per poll against a
third party. **Fix:** cache proxy status for a few seconds or make it non-blocking.

### A6 — LOW: unguarded env integer parsing
**File:** `app/config.py:69,93-95,200,249`; `ai_gate.py:32-49`. A malformed value
(`AI_MAX_CONCURRENCY=four`) raises `ValueError` at import → container won't boot with an
opaque traceback. **Fix:** wrap operationally-tuned ints in a helper that logs the
offending var and falls back to the default.

### (Structure) — `ai_coach.py` is oversized / over-coupled
`app/services/ai_coach.py` is 1642 lines / 82 KB, mixing coach orchestration, both
provider tool-loops (`_run_coach_conversation_openai:1287`, `_bedrock:1378`), food-search
fan-out, nutrition totals and reply generation, and is imported by every AI path. Not an
outage risk, but the module most likely to bite when moving AI off the single worker
(the CLAUDE.md end-state). Recommend splitting the two provider loops and the food-search
helpers into a `coach/` package.

## Track 2 — Backend correctness

### C1 — HIGH (data integrity): suggestion double-accept double-logs the MealLog ledger  ⟶ verified
**File:** `app/blueprints/social.py:519-548` (`respond_suggestion`).

Unlike the sibling `friend_accept` (`social.py:354-361`), which atomically claims the row
with a conditional `UPDATE ... WHERE status='pending'` before granting rewards,
`respond_suggestion` does an **unguarded check-then-act**:

```python
msg = Message.query.filter_by(id=msg_id, receiver_id=current_user.id).first_or_404()
if msg.message_type not in ("suggestion_meal", "suggestion_workout"): ...
is_meal = msg.message_type == "suggestion_meal"
if action == "accept":
    msg.message_type = msg.message_type + "_accepted"   # ← not atomic
    ...
    if is_meal:
        nutrients = _process_meal_suggestion_accept(msg)  # ← adds a MealLog row
db.session.commit()
```

**Trigger:** the user double-clicks "accept" (or the client retries). Two requests both
load `msg` with `message_type == "suggestion_meal"`, both pass the guard, both call
`_process_meal_suggestion_accept`, and both `db.session.add(MealLog(...))`. There is no
unique constraint on MealLog. **Wrong result:** the same meal is written to the canonical
ledger **twice**, double-counting the day's calories/protein and corrupting daily totals,
the protein nudge, and weekly reports — plus two duplicate reply messages to the sender.

**Fix:** claim atomically first, mirroring `friend_accept`:

```python
updated = Message.query.filter_by(id=msg.id, message_type="suggestion_meal")\
    .update({"message_type": "suggestion_meal_accepted"}, synchronize_session=False)
if not updated:
    db.session.rollback()
    return jsonify({"error": t("route.request_handled")}), 400
# only now process the meal / grant rewards
```
(Do the same for `suggestion_workout`.)

### C2 — LOW: `seed-quests` CLI seeds only 4 of 7 live quest types
**File:** `app/cli.py:13-18`. The CLI seeder defines `login`, `workout_logged`,
`suggestion_sent`, `meal_logged`. Runtime uses two more — `checkin_done`
(`tracking.py:228,308`) and `water_logged` (`training.py:342`) — which `db_init.py:137-138`
does seed at boot. Any env seeded only via `FITX_SKIP_DB_INIT=1` + `flask seed-quests` has
no `DailyQuest` row for those types, so `_claim_quest` returns `None` and those quests never
award XP. Masked in normal boot. **Fix:** align `seed_quests` defaults with the `db_init`
list. (Already noted `NEEDED_FIXES.md:65`.)

## Track 3 — Security & Auth

### S1 — MEDIUM: indirect prompt injection can reach the `manage_user_memory` write tool
**File:** `app/services/ai_coach.py:731` (tool); same-turn guard at `:454/:546/:670`.

Accepted-friend content (attacker-controlled `full_name`/activity text) is injected into
the coach context that ships alongside write-capable tools (`ai_coach.py:262-278`). The
same-turn stage→confirm lock protects meal/workout commits but does **not** cover
`manage_user_memory`. A successful injection could, in one turn, call
`manage_user_memory action="update"` to corrupt the **victim's own** health metadata (blank
`injuries`, set `dietary_restrictions`), later making the coach recommend contraindicated
exercises/foods.
**Bounds:** limited to the victim's own row (`user_id` is server-injected — no cross-user
pivot); success is probabilistic against existing guardrails (`_neutralize_friend_content`,
read-only fencing). Hence Medium.
**Fix:** extend the same-turn origination gate to `manage_user_memory` (ideally all
state-changing tools), or disable write tools on turns whose context includes third-party
friend data.

### S2 — LOW: image validation fails open under debug
**File:** `app/services/validators.py:52-55`. If Pillow is unavailable,
`_verify_image_bytes` returns `None` (accepts unverified bytes) when `current_app.debug` is
true. Correct in prod, but a misconfigured `FLASK_DEBUG=1` in production silently disables
magic-byte validation for all avatar/meal/pump-check uploads. **Fix:** fail closed
unconditionally, or gate the fail-open behind an explicit test-only flag.

### S3 — LOW: S3 stores attacker-declared MIME, not detected format
**File:** `app/services/validators.py:120-121` → `s3_helper.py:111,131`.
`_verify_image_bytes` confirms bytes are *some* allowed raster format but never checks the
true format equals the declared one; the declared MIME becomes the S3 `ContentType` and key
extension. `data:image/png;base64,<JPEG bytes>` is stored/served as `image/png`.
Metadata/data-integrity only (private bucket, presigned-URL access, allowlist excludes
SVG/HTML → no stored XSS). **Fix:** derive `content_type`/`ext` from Pillow's detected
`im.format`; reject a declared/actual mismatch.

### S4 — LOW: JWKS cache has no time-based TTL
**File:** `app/services/cognito_jwt.py:22,36-51`. `_jwks_cache` lives for the whole process
and only refreshes on an unknown `kid`; the parallel `cognito_service._get_jwks` uses a 6h
TTL. Not signature-forgeable (keys still verified); a rotated-out AWS key stays trusted
in-process until a new-`kid` token forces a refetch — self-heals in practice. **Fix:** add
the same time-based TTL and unify the two JWKS implementations.

### S5 — LOW: login user-enumeration via status code
**File:** `app/blueprints/auth.py:348-351`. Unconfirmed-but-registered accounts return
`403 + needs_verification`; bad credentials return `401`, distinguishing
registered-unverified accounts. Documented accepted tradeoff (M7); mitigated by per-username
rate limit and only leaks when Cognito `PreventUserExistenceErrors` is ON and the password
is already correct. **Fix (if enumeration matters):** collapse into a generic 401 and drive
the verify redirect from a non-authoritative signal.

### S6 — LOW: SSRF DNS-rebind pin is version-fragile
**File:** `app/services/menu_fetch.py:74-104` (`_pin_getaddrinfo`). The pin substitutes the
vetted IP only when the client calls `getaddrinfo` with a host string exactly equal to
`p.hostname`; otherwise it falls through to attacker-flippable resolution at connect time,
reopening the rebind TOCTOU. Not exploitable against installed requests/urllib3 (which
lowercases hosts) — version-dependent fragility, and it mutates process-global socket state.
**Fix:** pin per-connection via a custom `HTTPAdapter`/`PoolManager` that connects to the
resolved IP directly (preserving SNI/cert host); at minimum fail closed on an unexpected host.

### S7 — INFO: optional ownership guard on S3 helpers
**File:** `s3_helper.py:151,173`. `get_object_bytes`/`generate_presigned_url` skip
`_key_belongs_to` when `expected_user_id is None`. Not currently exploitable (every call site
passes an owner id; all keys originate from server-side DB columns). Future-facing risk.
**Fix:** make `expected_user_id` mandatory or default the guard to deny.

## Verified GOOD (no action needed)

- **IDOR/AuthZ:** every blueprint query scoped to `current_user.id`; records loaded by ID
  (`supplement_edit/delete`, `diary_*_item`, `pump_check_*`, `friend_accept/reject`,
  `respond_suggestion`) enforce ownership; `can_view_pump_check` re-checks *current*
  friendship.
- **CSRF/CSP:** Origin/Referer + per-session synchronizer token on all state-changing methods;
  no state-changing GET routes; per-request CSP nonces, no `unsafe-inline` for scripts; no
  `render_template_string`/`|safe`.
- **Injection:** SQL fully parameterized (`fitx_mcp/server.py` uses `%s` tuples; only
  `text("SELECT 1")`); no `os.system`/`eval`/`exec`/user-fed `subprocess`.
- **LLM boundary:** coach tools receive `user_id` server-injected from `current_user.id`;
  schema omits `user_id`; `_assert_principal` outside the swallowing try/except; LLM-supplied
  `s3_key` ownership-checked via segment equality.
- **JWT/session:** RS256 pinned (alg-confusion blocked); signature/iss/aud/token_use/exp all
  verified against JWKS over TLS; login selects the local user strictly from the verified
  `sub`; session fixation prevented (`session.clear()` before `login_user`); Fernet-encrypted
  tokens at rest; secure/httponly/SameSite=Lax cookies.
- **Correctness:** day-keys route through `app/timeutil`; streak/XP/quota/water/activity/
  pump-check counters use guarded conditional-UPDATE / `with_for_update` column reads with
  IntegrityError upsert fallbacks; weekly rollover idempotent via `WeeklyResetLog` UNIQUE;
  every MealLog writer passes through `clamp_serving_macros`; LLM JSON parsing is brace-bounded
  with `{}` fallback (no zero-macro ledger rows on parse failure).
- **Infra:** timeouts present on all reviewed network calls (OpenAI/Bedrock/FatSecret/wearables/
  menu_fetch/S3); migrations follow expand/contract (destructive DROPs gated `IF EXISTS` a
  release after data migration; `op.drop_column` only in `downgrade()`); Redis degraded-mode
  fallbacks correct (limiter in-memory, foodcache→L1, login throttle health cached 5s);
  dependencies fully pinned with Dependabot on the untrusted parsers.
