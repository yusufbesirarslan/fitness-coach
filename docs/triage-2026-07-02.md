_Result of a fresh 3-agent deep-dive triage (security · backend logic · structure/integrations) of the `fitness-coach` codebase. No code was changed during triage — this is the action list._

## Executive summary

The codebase remains **well-engineered and unusually security-conscious**. The security sweep found **no Critical, High, or Medium exploitable vulnerabilities** — every high-risk surface (auth/session, two-layer CSRF, per-request-nonce CSP, IDOR scoping, MCP authorization gate, SSRF defense on the menu scraper, secrets handling, upload validation) was verified as correctly mitigated.

The one finding that can corrupt **user-visible state** is a backend logic bug: the per-request weekly rollover computes the week boundary in **naive UTC instead of Istanbul time**, re-introducing exactly the misalignment a prior fix removed. That is the top priority. Everything else is hardening, maintainability, or operational.

## 1. Backend correctness

### 1.1 MED — Weekly rollover computes the week boundary in UTC, not Istanbul  ⭐ NEW, CONFIRMED
- **Where:** `app/hooks.py:197` → `app/services/gamification.py:157-170`.
- **Detail:** `maybe_weekly_rollover()` does `now = datetime.utcnow()` and passes that naive-UTC value into `run_weekly_rollover(now)` → `_last_completed_week_key(now)`. That function is explicitly documented (comment "B1": *"hafta sınırı ... Istanbul'da hesaplanmalı"*) to require Istanbul time and defaults to `app_now()`. The CLI path (`cli.py:weekly_reset_cmd` → `run_weekly_rollover(now=None)`) correctly uses Istanbul time; **only the per-request path passes UTC**, undoing the fix the B1 comment describes.
- **Scenario:** Between Istanbul Mon 00:00–02:59 (first hours of the new week), if the Istanbul-based cron is delayed/disabled and the per-request path fires the rollover at UTC Mon 00:00 (= Istanbul 03:00), it snapshots `weekly_xp` now polluted with 3h of *new-week* XP for the *previous* week's top-3 rewards, then `UPDATE user SET weekly_xp = 0` wipes that new-week progress. Rewards go to the wrong ranking and users silently lose XP. Today this is masked only because the cron usually runs first.
- **Fix:** Pass `app_now()` (or `None`) into `run_weekly_rollover`. The throttle key (`_rollover_throttle_passed`) can keep using `utcnow`; only the value handed to the rollover must be Istanbul-based.

### 1.2 LOW — Possible 500 when a session has NULL `target_calories`  ⭐ NEW
- **Where:** `app/blueprints/nutrition/plan.py:119,215,240,248`.
- **Detail:** `UserSession.target_calories` is nullable. `nutrition_plan_generate` only guards `if not last`, then builds the prompt with `round(target_calories)` (line ~240) *before* the try block (starts line 258). If a session has NULL `target_calories` (e.g. created/updated while the profile was incomplete — see `tracking.update_weight`, which can leave derived targets unset), `round(None)` raises `TypeError` → unhandled 500.
- **Fix:** Guard for a missing target and return `t("plan.no_session")` / 400, or move the `round()` inside the try.

### 1.3 LOW — `DailyActivity.date_key` is NOT NULL but has no default  ⭐ NEW
- **Where:** `app/models.py:438`.
- **Detail:** Sibling day-key columns — `MealLog.tarih` (216), `WaterLog.date_key` (401), `UserQuestProgress.date_key` (364) — all carry `default=lambda: app_today().isoformat()` as a safety net. `DailyActivity.date_key` is `nullable=False` with no default. The only current writer (`tracking.log_daily_activity`) passes it explicitly, so it isn't triggered today, but any future insert that omits it produces an IntegrityError instead of defaulting to today's Istanbul key.
- **Fix:** Add the same lambda default for consistency.

### 1.4 INFO — `foodcache` key-casing inconsistency  ⭐ NEW
- **Where:** `app/services/foodcache.py` + `app/blueprints/food.py:26-28`.
- **Detail:** `_cache_food_id`/`_get_cached_food_id` key on `name.lower()`; `_cache_macros`/`_get_cached_macros` key on the exact (case-sensitive) name. Consequence is only extra cache misses (never wrong data), so it's benign, but the two caches can disagree on a hit for the same query in different casing.
- **Fix (optional):** Normalize both to `.lower()`.

**Verified clean during triage:** `_today_nutrition_totals`, `menu.py` consumed, and `analytics_engine._check_protein_goal` all key on `MealLog.tarih` (ISO Istanbul) consistently; `calculate_tdee` activity multipliers match the profile form values; `complete_workout` (PumpCheck day-idempotency + single-transaction XP/quest/WorkoutLog with IntegrityError rollback), `set_water`/`log_daily_activity` race handling, `run_weekly_rollover` idempotency (WeeklyResetLog unique), `update_streak` row-locking, and `reward_dismiss`'s zero-padded `max(week_key)` are all correct. (Note: the "utcnow %d.%m" comment at `ai_coach.py:316` is stale/misleading but the code is correct.)

## 2. Security

> **No Critical / High / Medium exploitable vulnerabilities.** The items below are Low / informational, all verified against actual code. This confirms and extends the prior audit in `NEEDED_FIXES.md §2`.

### 2.1 LOW — Existence oracle via 404-before-403 ordering  ⭐ NEW
- **Where:** `app/blueprints/social.py` (`friend_accept` ~155, `friend_reject` ~182, `respond_suggestion` ~314) and `app/blueprints/supplements.py` (`edit` ~93, `delete` ~138).
- **Detail:** These call `get_or_404(...)` and *then* return 403 on ownership mismatch. An attacker iterating IDs can distinguish "exists but not yours" (403) from "doesn't exist" (404) — a minor cross-user record-enumeration oracle. No data is disclosed. Diary routes already avoid this (404 in both cases).
- **Fix:** Return 404 for both not-found and not-owned.

### 2.2 LOW — Image content verification fails open if Pillow is missing  ⭐ NEW
- **Where:** `app/services/validators.py:52-54` — `_verify_image_bytes` returns `None` (accept) when Pillow can't be imported.
- **Detail:** Production ships Pillow, so this only affects local dev, but it means the "is this really an image / decompression-bomb" check is skipped whenever the dependency is absent.
- **Fix:** Fail closed in non-dev environments.

### 2.3 LOW — State-changing work on a GET route (`/referral`)  ⭐ NEW (not exploitable)
- **Where:** `app/blueprints/pages.py:68` — `GET /referral` lazily calls `ensure_referral_code(current_user)` + `db.session.commit()`.
- **Detail:** It only assigns the current user's own code, is idempotent, and takes no attacker-controlled input, so it isn't CSRF-exploitable — but it bypasses the write-method CSRF gate by design.
- **Fix (hygiene):** Assign the referral code at registration instead of on GET.

### 2.4 LOW — Account-enumeration signals (accepted, documented tradeoffs)
- `auth.py:227` surfaces `UserNotConfirmedException` distinctly (needed for the `/verify` UX; guarded by Cognito `PreventUserExistenceErrors` + per-username rate limit).
- `_login_username_key` (auth.py:66-79) lets an attacker burn a victim's failure budget to cause a short, self-healing lockout window.
- Both are explicitly reasoned about in comments — noted for completeness, no change required.

### 2.5 INFO — Referer-only CSRF fallback
- `app/hooks.py:141-151`: when `Origin` is absent, the guard falls back to a `Referer` host check. Weaker, but Layer 2 (synchronizer token) always runs regardless, so not independently exploitable.

### 2.6 Reconfirmed still-open from `NEEDED_FIXES.md`
- **§2.1 MCP HTTP transport has no authorization (by design, gated).** Re-verified: HTTP transport requires `FITX_MCP_ALLOW_HTTP=1` and binds only to `127.0.0.1:8100`; never started in `docker-compose.yml`, never exposed by `nginx.conf`; in-process use injects `current_user.id` and re-checks via `_assert_principal`; SQL fully parameterized. **Risk is purely operational** — never place it behind a public reverse proxy. `tests/test_mcp_gate.py` defends this.

**Verified SOLID (not vulnerable):** `SECRET_KEY` required in prod, Secure/HttpOnly/SameSite cookies, session-fixation defense + `session_protection="strong"`, constant-time password compare with dummy-hash, per-IP + per-username throttles with `LOGIN_FAIL_CLOSED`; two-layer CSRF as global `before_request`; full CSP with per-request nonce, no `unsafe-inline`; IDOR scoping on every by-ID load; SSRF defense with DNS-rebind pinning; no hardcoded secrets, FatSecret TLS enforced; upload validation with Pillow `verify()` + pixel/size caps; prompt-injection cannot pivot cross-user (`_dispatch_coach_tool` uses server-injected `user_id`).

## 3. Structure / integrations / infra

### 3.1 HIGH (ops) — Single worker + 8 threads with blocking AI calls = app-wide availability risk  ⭐ NEW
- **Where:** `Dockerfile` (`--workers 1 --threads 8 --timeout 300`), `app/services/ai_coach.py`, `app/services/ai.py`.
- **Detail:** Every OpenAI/Bedrock call is synchronous. The `/ask` coach loop can issue up to 5 sequential model calls (`_COACH_TOOL_LOOP_CAP`), each with 30s (OpenAI) / 60s (Bedrock) client timeouts under a 300s gunicorn timeout, across only 8 threads for the *entire* app. As few as 8 concurrent coach/menu/plan requests can saturate all threads, starving logins, `/health` probes (which then flip the container `unhealthy` → possible restart), and static pages. `AI_CHAT_QUOTA` (default 200/week) and rate limits blunt but don't remove this.
- **Fix:** Move AI endpoints to a separate worker pool / async path or offload long AI work to a queue; raise worker count once the single-worker invariant is removed. At minimum, document the concurrency ceiling as a known operational limit. (Extends `NEEDED_FIXES.md §3.10`.)

### 3.2 MED — Deploy has no health-gate / rollback  ⭐ NEW
- **Where:** `.github/workflows/deploy.yml`.
- **Detail:** Deploy does `git reset --hard origin/main && docker compose up -d --build`, then *observes* (`docker compose ps`, `logs`, `curl /login`) but never *acts* on failure — the old container is already replaced. A build that boots crash-looping/unhealthy takes the site down with no automatic recovery; the SSM job can even report Success while the app is broken (the curl output isn't asserted on).
- **Fix:** Gate on `/health` returning 200 after boot and roll back (redeploy previous image/commit) on failure; assert on the curl status.

### 3.3 LOW–MED — ~330 lines of unreachable dead code in `training_plan_generate`  ⭐ NEW
- **Where:** `app/blueprints/training.py:68-399`.
- **Detail:** The function unconditionally returns (or raises) inside the try at lines 53-66 (`return jsonify(generate_training_plan_payload(...))`). Everything from line 68 on — the legacy prompt build, injury-persistence block (224-235), and the injury contraindication safety-net (346-363) — never executes. The logic is faithfully reimplemented in `app/services/training_generation/service.py`, so there's no current runtime regression; the hazard is that two copies can drift and edits to the visible block silently no-op.
- **Fix:** Delete lines 68-399.

### 3.4 MED — `ai_coach.py` is a 1,512-line god-module  ⭐ NEW
- **Where:** `app/services/ai_coach.py`.
- **Detail:** Mixes six concerns: coach system prompt + i18n, all 8 DB-mutating tool implementations, the tool registry (`_COACH_TOOL_DEFS`), the OpenAI tool-loop, the Bedrock tool-loop, and the legacy single-shot `generate_coach_reply`/`generate_checkin_feedback`. Largest maintainability liability; also participates in an import cycle resolved with a function-local import (`from fitx_mcp.server import ...` inside `_fetch_coach_context`).
- **Fix:** Split into `coach_prompts.py`, `coach_tools.py` (implementations + registry), and `coach_runtime.py` (the two provider loops).

### 3.5 MED — `CLAUDE.md` documentation drift  ⭐ NEW
- **Where:** `CLAUDE.md` vs. reality.
- **Detail:**
  - Header says "Flask + SQLAlchemy + OpenAI (gpt-4o-mini) + FatSecret." Reality adds a **primary Bedrock/Claude Sonnet path** (`BEDROCK_*`, `_heavy_chat`, `bedrock_client`), **Cognito OIDC** login, **S3**, and **Redis** — none in the summary.
  - The `docker-compose.yml` description ("web + db (postgres) + redis") is stale: the bundled `db` service was **removed** (now external RDS via `DATABASE_URL`); compose only defines `web` + `redis`.
  - The `app/services/` list omits `premium.py`, `referral.py`, `cognito.py`, `cognito_idp.py`, `avatars.py`, `injury_constraints.py`, and the entire `training_generation/` subpackage.
- **Fix:** Refresh the stack line, compose description, and services inventory.

### 3.6 MED — FatSecret client: no connection pooling or retry  ⭐ NEW
- **Where:** `app/services/fatsecret.py` (`_fs_get`/`_fs_post`).
- **Detail:** Calls use module-level `requests.get/post` directly — no `requests.Session`, pooling, or retry adapter. Under 8 threads doing per-menu-item lookups each call pays a fresh TCP+TLS handshake, and a single transient blip fails the lookup (degrades gracefully to LLM/static). Timeouts are set; token fetch is well-guarded.
- **Fix:** Use a shared `Session` with `HTTPAdapter(max_retries=Retry(total=2, backoff, status_forcelist=[429,502,503,504]))`.

### 3.7 LOW — OpenAI coach tool-loop lacks per-call error mapping  ⭐ NEW
- **Where:** `app/services/ai_coach.py` `_run_coach_conversation_openai` (~line 1183).
- **Detail:** The `openai_client.chat.completions.create(...)` inside the loop isn't wrapped; a transient provider error propagates to `/ask`'s generic `except` → HTTP 500 (`coach.reply_failed`), whereas the Bedrock loop degrades gracefully. So OpenAI-path coach failures surface as 500s while Bedrock-path failures don't. Also, `/chat` (Bedrock-backed `generate_coach_reply`) is rate-limited but **not** quota-gated, unlike `/ask` — a minor freemium inconsistency.
- **Fix:** Wrap the loop's `create()` and reuse the friendly-fallback path; decide whether `/chat` should also be quota-gated.

### 3.8 LOW — Verbose INFO logging on the hot FatSecret/menu path  ⭐ NEW
- **Where:** `app/services/fatsecret.py`.
- **Detail:** The macro-lookup path emits many `logger.info(...)` lines per food item (per method attempt, per serving, per match/skip). On the menu pipeline (many items × candidates) this is high-volume production noise that adds cost. (Overlaps `NEEDED_FIXES.md §1.6/1.7` deferrals.)
- **Fix:** Demote per-item/per-serving traces to DEBUG; keep totals/warnings at INFO.

### 3.9 Reconfirmed still-open infra from `NEEDED_FIXES.md`
- **§3.3** Deploy CSP cleanup via fragile inline `sed` on the live nginx config — render the full site config from the repo, or fail the deploy if a stray `add_header Content-Security-Policy` remains.
- **§3.4** HSTS/TLS depends on `certbot --nginx` having mutated the config; commit an explicit 443 block + 80→443 redirect, or document the certbot dependency.
- **§3.11** `docker-compose.yml` `restart:` inconsistency; `psycopg2-binary` discouraged for prod by maintainers (acceptable on slim).

**Verified strong during triage:** clean application-factory pattern, lazy guard-imported LLM/boto3/Authlib/Sentry clients, layered AI error/fallback (Bedrock→OpenAI fallback, JSON salvage), S3 IAM-profile auth (no keys) with SSE + presigned expiry + ownership scoping, Redis graceful memory fallback + `/health` degraded state, DB auto-upgrade with kill-switch + auto-stamp of legacy DBs, CI `flask db check` schema-drift guard (blocking), fully pinned requirements + digest-pinned Dockerfile base + Dependabot, and a ~55-file test suite.
