## 1. Medium — Challenge event funnel drops repeat-per-day increments → `weekly_meals` is uncompletable

**Files:** `app/services/gamification.py:306-317` (`complete_quest_for_user`),
`app/services/gamification.py:273-303` (`_claim_quest`),
`app/services/challenges.py:64-116` (`record_event`);
callers `app/blueprints/nutrition/meallog.py:123,194`,
`app/blueprints/nutrition/diary.py:157,421`,
`app/blueprints/training.py:322-347` (water).

### Root cause (one mechanism, two visible symptoms)

`_claim_quest` fires `record_event(user_id, quest_type)` at the **top**
(gamification.py:282), *before* the once-per-day quest dedup, so that challenge
progress is recorded even without a `DailyQuest` row. `record_event` writes the
`UserChallengeProgress.progress += amount` increment inside a
`db.session.begin_nested()` **savepoint** — it is **staged, not committed**
(challenges.py:95-108). Whether that staged increment survives depends entirely
on whether the *caller* commits:

- **`_claim_quest` + an unconditional caller commit** — e.g. the workout path
  (`training.py:229` → `db.session.commit()` at `:234`), and the paths that call
  `record_event` directly (`pump_check_created`, `active_day`, `xp_earned`).
  The increment persists on **every** event. ✅ Correct for *event-count*
  challenges.

- **`complete_quest_for_user`** (meals via `meallog.py`/`diary.py`, water via
  `training.py:347`):

  ```python
  def complete_quest_for_user(user_id, quest_type):
      result = _claim_quest(user_id, quest_type)   # record_event stages +1 (savepoint)
      if result is None:
          return None                              # ← returns WITHOUT db.session.commit()
      try:
          db.session.commit()
      ...
  ```

  `_claim_quest` returns `None` whenever today's `DailyQuest` is already claimed
  (gamification.py:292-293). On the **2nd+ action of the day**, the staged
  challenge increment is therefore left pending and **rolled back** at
  request teardown (`db.session.remove()`). Only the day's **first** action —
  the one turn where the daily-quest claim succeeds and the commit runs —
  persists an increment.

### Symptom A (real bug): `weekly_meals` can never be completed

`weekly_meals` ("log **10** meals this week", `challenges.py:149-151`,
`metric="meal_logged"`, `target_value=10`) is an *event-count* challenge but
runs through `complete_quest_for_user`. It therefore accrues **at most 1/day =
7/week < 10 → uncompletable.** Verified end-to-end: `meallog.commit_once`
commits the `MealLog`, then `complete_quest_for_user("meal_logged")` runs; on
every meal after the first each day the increment is discarded.

### Symptom B (latent trap): the "obvious" fix breaks `weekly_water`

`weekly_water` ("track water on **5 days**", `challenges.py:152-154`,
`metric="water_logged"`, `target_value=5`) is a *day-count* challenge, and the
water route calls `complete_quest_for_user("water_logged")` on **every** water
write (`training.py:346-347`). It currently works **only by accident** — the
same commit-skip caps it at 1/day, which happens to match "5 days".

The tempting fix (make `complete_quest_for_user` commit regardless of `result`)
**fixes meals but breaks water**: every glass tap would then persist an
increment, so 5 taps in one day would complete a challenge meant to require 5
separate days. (This is the over-counting the concurrency agent flagged; it is
masked *today* by the commit-skip, and would become real under a naive fix.)

### Fix (must be metric-aware)

Do **both**, together:

1. In `complete_quest_for_user`, commit even when `result is None` so
   event-count challenge increments survive (a cheap no-op when nothing is
   pending):

   ```python
   def complete_quest_for_user(user_id, quest_type):
       result = _claim_quest(user_id, quest_type)
       try:
           db.session.commit()
       except Exception:
           db.session.rollback()
           return None
       return result
   ```

2. Make *day-count* metrics fire the challenge event **once per day** instead of
   per write. Cleanest: fire `record_event("water_logged")` only on the
   no-row→row transition in `training.py:322-340` (first water log of the day),
   or day-scope those metrics inside `record_event` itself. Do the same audit
   for any future "N days" challenge (`active_day` is already correctly
   day-gated via the FOR-UPDATE branch of `update_streak`, `hooks.py:311`).

Add a regression test that logs 10 meals across 4 days and asserts
`weekly_meals` completes, and logs water 5× in one day and asserts
`weekly_water` progress == 1.

## 2. Medium — Deleting a "quote" never decrements `reposts_count` → permanent counter drift

**Files:** `app/blueprints/social.py:296-298` (increment) vs `:319-328`
(decrement).

`feed_repost` increments `PumpCheck.reposts_count` **unconditionally** for both
`mode="repost"` and `mode="quote"` (line 296 has no mode guard, and the endpoint
returns `repostsCount` for quotes — so quotes are meant to count as shares).
But `feed_item_delete` decrements only when `is_repost = item.item_type ==
"repost"` (line 320) inside `if is_repost and ref_id is not None:` (line 323).

**Failure scenario:** user quotes pump-check #42 → `reposts_count` = 1; user
deletes their quote → `item_type == "quote"` → `is_repost` False → **no
decrement** → `reposts_count` stays 1 forever with zero live reposts. The
"shares" number on every pump-check card (`pump_checks.py` → `repostsCount`)
drifts monotonically upward and never self-corrects. Trivially user-triggerable.

**Fix:** in `feed_item_delete`, decrement whenever the deleted item references a
pump check, matching the create side — replace `if is_repost and ref_id is not
None:` with `if ref_id is not None:` (`ref_id` is already `None` for
non-pump-check items). Consider a one-off reconciliation query to correct
already-drifted counters.

## 3. High — Destructive-migration rollback has no reliable backstop *(still unfixed — prior #1)*

**File:** `.github/workflows/deploy.yml:66-81, 94`

The health-gate rollback does `git reset --hard $PREV_COMMIT && docker compose
up -d --build` — it reverts **code only**, never the DB (documented as A2 in
CLAUDE.md: boot auto-applies migrations; rollback does not undo them). The sole
mitigation, a pre-deploy RDS snapshot, is `continue-on-error: true` **and**
silently `exit 0`-skips entirely when `vars.RDS_INSTANCE_ID` is unset.

**Failure scenario:** a forward-applied destructive migration (column/table drop
or rename) + rolled-back code = unrecoverable state, with **zero backup** if
`RDS_INSTANCE_ID` isn't configured — and the pipeline still reports the snapshot
step green. The single scenario that can lose real user data irrecoverably.

**Fix:** make the snapshot step **blocking** (fail the deploy if
`RDS_INSTANCE_ID` is missing or `rds:CreateDBSnapshot` is denied); keep enforcing
the existing expand/contract migration discipline for anything destructive.

## 4. Low–Medium — Wearable token refresh has no mutual exclusion

**Files:** `app/services/wearables/adapters.py:117-146` (`refresh_access_token`,
no lock), `app/services/wearables/tokens.py:58-99` (`save_wearable_tokens`);
concurrency acknowledged at `app/services/wearables/sync.py:92-95`.

`refresh_access_token` reads the connection (no row lock), checks expiry, POSTs
the refresh token, then overwrites via `save_wearable_tokens`. Nothing
serializes two concurrent refreshers (1 gunicorn worker / 8 threads; a manual
`POST /sync` racing a `GET /sleep`).

**Failure scenario:** near expiry, two threads read the **same** old refresh
token and both POST it. WHOOP **rotates** refresh tokens, so the second call
holds an already-invalidated token → 4xx → `raise_for_status()` → request fails
(502). Best case a transient 502 that self-heals next sync; worst case
(providers that treat rotated-token reuse as a breach and revoke the token
family) the connection is stuck at `reauth_required` and the user must reconnect.

**Fix:** serialize refresh per `(user, provider)` — `SELECT … FOR UPDATE` on the
`UserWearableConnection` row (or a short Redis lock) at the top of
`refresh_access_token`, re-read expiry inside the lock, and skip the network
refresh if another thread already refreshed (double-checked locking).

## 6. Low — Challenge completion that fails mid-reward can strand `progress ≥ target` with `completed_at = NULL`

**File:** `app/services/challenges.py:105-116, 118-140`.

`_try_complete` runs the guarded `UPDATE … SET completed_at WHERE completed_at
IS NULL`, then `award_xp` / `award_badge` / `notify` / `log_activity` — all
inside the per-challenge `begin_nested()` savepoint. If any reward step raises,
the `except Exception` at `:111` rolls back the **whole savepoint**, reverting
both `completed_at` and the progress increment.

**Failure scenario:** the user's final qualifying event pushes `progress ==
target`; a transient error in `award_badge`/`notify` rolls the savepoint back →
progress drops below target again. Self-heals only if the user triggers the
metric again; if it was their last action of the week for that metric, the
earned challenge is silently never completed (no XP/badge). Narrow, boundary-
only, self-healing in the common case.

**Fix:** commit the guarded `completed_at` write independently of the reward
side-effects (or make reward failures not revert progress/completion — retry
rewards separately).
