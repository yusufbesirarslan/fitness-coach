# R6 repair-SHA handoff

This procedure covers a **prepared, uncommitted, same-head adult cutover** whose original immutable image keeps failing application verification after fresh starts. It requires a separate production incident decision, protected workflow approvals, and evidence review when used. A missing or unreadable receipt, schema-changing release, uncertain migration cleanup, or unresolved opening/commit of the failed revision is outside this handoff.

## Before accepting repair source

The incident commander names a production operator and independent verifier. Freeze release and route operators. The verifier binds the exact protected failed job/run/attempt, exact failed SHA/tree and immutable image, availability of its encrypted manual snapshot, the original prepared receipt and its canonical JSON SHA-256, disposable and incident boot evidence showing a failure across fresh starts, and whether registration ever opened. Resolve any ambiguous opening/commit before using this path. Review the exact descendant repair source, its entire release diff and exact CI. The actual resulting main SHA must have successful exact main-push CI before the repair's protected workflow. A draft SHA or a tree-equivalent squash alias has no incident authority.

The separately authorized operator quarantines the failed pair before the stage. The prior boot-local procedure supplies the exact web identity/readback method. For the handoff, also explicitly authorize quarantine of the verified failed worker by its full Docker ID, StartedAt, baked revision and immutable image, or verify its absence. Under the canonical production flock followed by the canonical route flock, prove the failed web's boot-bound registration was closed and its local open receipt absent, verify incident source/image/actor bindings, then stop the exact failed actors with bounded graceful shutdown. Read back `Running=false, Pid=0` and the same immutable identity/start time, prove sockets and worker processes absent, then remove only those exact stopped Docker IDs. Preservation of the immutable failed image and original receipt is mandatory. Capture actor evidence before removal. A Docker timeout, boot drift, foreign actor, or uncertain closure requires locked observation and independent disposition. If admission or durable commit could have succeeded, preserve the serving pair and hold the repair handoff. The incident commander and founder explicitly accept outage duration and in-flight work risk.

Leave both slots empty. Verify that all application ports 5000, 5001 and 5002 have no listener, including loopback listeners outside Docker, and no established backend requests remain. Under the canonical outer lock, use the installed route helper to bring the canonical route to the original **empty old slot** if it was aimed at the failed candidate port. The helper acquires its own canonical route lock. Use its strict status/marker readback. An unknown route or competing operator is HOLD. Never start a previous writer. Capture the unchanged nginx configuration, actor evidence and empty listener and socket proof before and after convergence. Release both locks before requesting the protected stage. The transaction independently rechecks the empty route and retires the prior nginx generation before allowing a repair to start. Normal production deploys, including all concurrent and out-of-band operations, must honor the canonical outer lock. No standalone nginx edits or Docker/route activity overlaps this procedure.

The sanitized incident evidence document binds those proofs, its timestamps, the environment and database identity, the verified original snapshot, protected failed attempt/job and attribution to the same immutable image across distinct boots. Preserve it in the operator's incident record. Its SHA-256 is an authorization input. The controller checks the approval's structure and attempt identity, independently rechecks the retained original snapshot, and checks the host's original receipt. The independent verifier owns the evidence contents and approves the hash. The original `#544` receipt alone does not identify the protected job or rule out an open-before-fsync interruption.

## Protected stage and apply

The production-environment variable `R6_REPAIR_AUTHORIZATION` is single-attempt authority. Reserve this name for the production environment. Verify there is no repository or organization variable of that name, and remove the environment value after use. It cannot be used alongside `R6_FORWARD_RECOVERY_AUTHORIZATION`. Exact main/CI and workflow identity, production reviewers and concurrency, production OIDC, protected host delivery, host lock and exact Git archive checks remain in force. The strict F3 operational gate continues to apply.

| Attempt | Required exact authorization |
| --- | --- |
| Stage | `repair-stage:<repair-sha>:<run>:<attempt>:<repair-tree>:<failed-sha>:<failed-tree>:<original-receipt-sha256>:<failed-run>:<failed-attempt>:<failed-job>:<failed-snapshot-id>:<incident-evidence-sha256>` |
| Apply | `repair-apply:<repair-sha>:<same-run>:<higher-attempt>:<staged-receipt-sha256>:sha256:<image-id>:<failed-snapshot-id>` |

1. Authorize the stage only after independent source and incident review. The protected controller re-verifies the retained failed snapshot on the exact database and obtains a distinct encrypted manual snapshot with an independent Available readback. Under the normal outer flock, the host validates source ancestry and both trees. The old, failed and repair migration subtrees must be byte-identical. It validates checkout, both slots empty, old-slot route, no former worker, neither prepare container present, the full live head set and verified completion fence. It builds once from the exact candidate archive. It records the exact baked revision and immutable image ID in the durable stage receipt. No serving actors, schema mutations, registration opening or normal deploy completion occur during staging.
2. The independent verifier checks the returned exact archive/build/tree/image, staging snapshot, canonical receipt digest and incident evidence. Before work is accepted, a distinct founder authorization pins that staged image and receipt to a later attempt of the same workflow run. Re-run the protected deploy job under the same run and obtain the new attempt's production approval. If GitHub no longer permits that rerun or main has moved, hold the incident. If stage delivery was interrupted after persisting the receipt, safely read the exact durable record and prove its provenance before the founder can authorize apply. A stage authorization cannot restage over the record or run the release. Every new apply requires a new attempt and fresh Available snapshot. The host consumes each valid apply attempt under the outer lock before writer start. An interrupted consumed attempt is never replayed.
3. The first apply checks there are still no prior writers or live requests in either slot. The route remains on the empty old slot. Under production and route authority, reload and prove retirement of the earlier nginx generation before the new repair may boot in the other slot. Inherit the original prepared state only after the immutable migration graph, exact read-only live schema proof and completion fence are independently verified again. No migration or `release-prepare` runs in the handoff. Use the original staged immutable image, with no rebuild. Pre-switch verification, canonical route switch, public and mobile ingress, exact worker, old-backend absence, eligibility, real web/worker ACL and pooled UTC, floor/fence, checkout, and boot-bound admission open/readback all remain required. Then commit the receipt, verify retirement and emit normal completion evidence.
4. A subsequent separately authorized attempt may resume the same repair. If it already routed a previously verified repair, it re-verifies the existing exact container without starting a replacement behind that route. A missing, stopped or unverifiable routed repair requires incident handling first. If refencing for a new boot, repeat authorized quarantine and prove the empty old route. The protected retry repeats the initial generation retirement before starting on the other slot. The repair itself may remain defective. Preserve and hold the receipt, image and incident evidence. A different SHA cannot replace the staged repair. The currently verified repair remains active after commit and the next distinct protected normal release can begin from that slot. The next release archives the committed incident receipt before replacing the active journal.

The versioned active record in the deployment Git metadata stores the original receipt, stage authorization and its human-verified evidence digest, both source trees, original failed attempt and snapshot, repair image and live schema heads, latest consumed apply attempt and snapshot, and durable commit status. Its immutable stage digest binds all stage fields. Record replacement preserves mode 0600 and synchronizes the file and directory. An older parser refuses the versioned receipt. Code and evidence assume the host's production deploy account, Git metadata and Docker daemon remain trusted, as for the existing protected workflow.

## Post and watch

The offline-qualified checker accepts repair evidence only when bound explicitly to `repair-apply`, approved source/tree, verified diff, exact main-push CI, the latest protected workflow attempt/job, the independently reviewed staged receipt and both immutable images. It checks retained and fresh Available snapshot markers, ordered handoff/registration/commit/retirement, and the exact live repaired web and worker container IDs and boot times. `post`, `post2`, `watch1` and `watch2` refuse stage-only, interruption, retired-container evidence, a failed applicable alarm or any result with committed residue. No live binding or post/watch execution is authorized by source qualification.
