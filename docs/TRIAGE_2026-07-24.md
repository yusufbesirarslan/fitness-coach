## A-1 — [Medium, NEW] Deploy `/health?deep=1` gate is likely silently degraded to the shallow body

**Files:** `app/__init__.py:17-48` (`_deep_health_networks`/`_deep_health_allowed`, default CIDR `172.17.0.1/32`), `:102-136` (deep block incl. login-offline→503 escalation); `.github/workflows/deploy.yml:94` (`curl … http://127.0.0.1:5000/health?deep=1` **from the host**); `docker-compose.yml` (no explicit `networks:` stanza); `.env.example:120`; `tests/test_health.py:100` (bakes in the same `172.17.0.1` assumption).

The deep gate's purpose (comments at `app/__init__.py`) is to return **503** when the DB is green but login is offline (Redis down + `LOGIN_FAIL_CLOSED=1`) so a broken deploy auto-rolls back. That escalation lives **inside** `if request.args.get("deep") == "1" and _deep_health_allowed():`.

`_deep_health_allowed()` trusts only loopback or `DEEP_HEALTH_TRUSTED_CIDRS` (**default `172.17.0.1/32`**). But the deploy gate curls `127.0.0.1:5000` **from the host** — the container therefore sees the connection's source as the **docker bridge gateway**, not loopback. Because `docker-compose.yml` declares no explicit network, Compose creates a *project* bridge (`fitness-coach_default`) whose gateway is typically `172.18.0.1`/`172.19.0.1` — **not** `172.17.0.1` (that belongs to Docker's *default* `bridge`, which these services don't use).

**Result:** with the default config, `_deep_health_allowed()` returns **False** for the deploy probe → the deep block is skipped → the endpoint returns the **shallow 200** body → the gate passes **even when login is 100% down**. The safety net is disarmed unless the operator happened to set `DEEP_HEALTH_TRUSTED_CIDRS` to the real Compose gateway. `tests/test_health.py:100` encodes the same wrong assumption, so the suite gives false confidence.

**Verified this pass:** default CIDR is `172.17.0.1/32` (`app/__init__.py:21`); `deploy.yml:94` curls from host loopback; no `networks:` stanza in compose. *Plausible* (not Confirmed) only because prod may override `DEEP_HEALTH_TRUSTED_CIDRS` and userland-proxy behavior can't be observed here — but the shipped default is the wrong gateway.

**Fix (robust):** curl from **inside** the container so it is genuine loopback and always allowed, independent of subnet:
`docker compose exec -T web curl -s -o /dev/null -w '%{http_code}' localhost:5000/health?deep=1`.
Alternatively pin `DEEP_HEALTH_TRUSTED_CIDRS` to the actual compose gateway and add a test that **derives** the gateway rather than hardcoding `172.17.0.1`.

## A-2 — [Medium] `_model_slots.acquire()` no-timeout + ungated callers breach the `/health` thread reserve

**Files:** `app/services/ai_gate.py:52` (`_model_slots = BoundedSemaphore(AI_MODEL_MAX_CONCURRENCY)`), `:57-64` (`model_concurrency_slot` — `.acquire()` **no timeout**); ungated callers `app/blueprints/food.py` (`food_search` → `_coach_search_food → _food_search_llm → _heavy_chat → _claude_chat/_openai_chat`) and `app/blueprints/social.py:881` (`respond_suggestion`); reserve math `ai_gate.py:70`.

The "reserve 2 threads for `/health`" invariant counts only `_ai_slots` + `_scrape_slots`. `model_concurrency_slot()` is a **third** semaphore acquired with **no timeout** by routes that are **not** behind `ai_concurrency_gate` and carry only a per-user rate-limit (which does not stop *different* users). A cross-user burst of `food_search` cache-misses can park all 8 gunicorn threads blocked on `_model_slots.acquire()` → `/health` queues behind AI work → false rollback / restart loop — exactly what the reserve exists to prevent. Confirmed independently by both the correctness and architecture audits.

**Fix:** bounded `acquire(timeout=…)` in `model_concurrency_slot` returning 503 on exhaustion, and/or fold the ungated model callers into the reserve invariant.

## A-3 — [Low–Medium] `weekly_water` challenge counts toggle-events, not days

**Files:** `app/blueprints/training.py:425` (`set_water` fires the funnel only on `count>0 and prev_count==0`), `app/services/challenges.py:110-124` (`record_event` — weekly `period_key` only, blind `progress = progress + amount`, **no per-day dedup**).

`prev_count` is read from the mutable `WaterLog.count` and `count` is client-supplied (clamped 0..8). Sequence on one Istanbul day — `count=5` (fires) → `count=0` (no fire) → `count=5` (fires again) — drives a "log water 5 days" challenge (target 5) to completion in one afternoon and awards its XP. DailyQuest XP is safe (deduped by `UserQuestProgress` per `date_key`); only the challenge counter inflates. The inline comment claiming parity with `active_day` is wrong — `active_day` fires from a `FOR UPDATE`-locked once-per-day branch in `hooks.py` and is genuinely idempotent; `prev_count==0` is not.

**Fix:** per-Istanbul-day idempotency key for day-semantic metrics (persist `last_event_day` on the progress row), or gate the emit on a persisted "first positive log today" marker.

## A-4 — [Low] OpenAI non-stream coach loop has no per-turn wall-clock budget

**File:** `app/services/ai_coach.py` (`_run_coach_conversation_openai`, ~`:1013-1023`).

The Bedrock non-stream and stream loops honor `_coach_turn_deadline`/`_remaining_coach_turn_seconds`, but the OpenAI fallback loop still runs up to `_COACH_TOOL_LOOP_CAP` (5) × 30 s ≈ 150 s per turn, each round holding `_ai_slot` + `_model_slot` + web thread. When Bedrock is down and all turns route to OpenAI, this compounds A-2's starvation (bounded only by gunicorn `timeout=300`).

**Fix:** apply `timeout=min(30, remaining)` from the same deadline helper to the OpenAI loop.

## A-5 — [Low–Medium, NEW] No app-level `MAX_CONTENT_LENGTH` — body-size DoS if nginx is bypassed

**Files:** app-wide (`grep MAX_CONTENT_LENGTH` → **zero matches**, verified this pass); only cap is `nginx.conf:87` `client_max_body_size 25m`. Per-field limits (avatar 500 KB `avatars.py:15`; pump/meal 8 MB base64 `validators.py:128,146`) all run **after** `request.get_json()` has buffered the whole body into memory.

Any path reaching gunicorn without the host nginx cap (direct-to-loopback, internal network, or a future ingress change) has **no app-layer body limit** → arbitrarily large JSON read into memory on the single gunicorn worker (8 threads). Even under the 25 MB edge cap, 8 concurrent 25 MB bodies ≈ 200 MB transient plus base64-decode copies → memory-exhaustion / thread starvation. The app depends entirely on an infra control it does not own.

**Fix:** set `app.config["MAX_CONTENT_LENGTH"]` (~10 MB) in `app/config.py` so the cap survives an nginx misconfig.

## A-6 — [Low] `ProxyFix` trusts `X-Forwarded-Host`/`-Port` the proxy never sets

**Files:** `app/config.py:241` (`ProxyFix(..., x_host=1, x_port=1)`); `nginx.conf:107-124` sets only `Host`, `X-Real-IP`, `X-Forwarded-For`, `X-Forwarded-Proto` — never `X-Forwarded-Host`/`-Port`.

A client can send `X-Forwarded-Host: evil.com` and ProxyFix overwrites Flask's host → `request.host_url`, `url_for(_external=True)` reflect the attacker value. **Not a CSRF bypass** — Layer 1 (Origin vs `request.host_url`) could match a spoofed host, but Layer 2 (per-session synchronizer token) still holds; logout is separately guarded by `Sec-Fetch-Site`. Blast radius is self-inflicted external-URL generation (e.g. referral link `pages.py:75`).

**Fix:** `x_host=0, x_port=0` (nginx forwards correct `Host` natively), or have nginx set those headers explicitly.

## A-7 — [Low, NEW] Streamed fallback text can be persisted to coach memory on client disconnect (B16 gap)

**File:** `app/services/ai_pipeline.py:245-255` (the `GeneratorExit` / client-disconnect path: `partial = "".join(parts).strip(); if partial: _record(conversation, question, partial, interrupted=True)`).

The `done`/`error` branches correctly route text through `finalize_reply`, so a classified error-fallback is **not** persisted. But when the Bedrock tool loop exhausts its budget/cap, `ai_stream._emit_text(...["tool"])` streams the fallback string ("İşlemi tamamlayamadım, tekrar dener misin?") as delta chunks (appended to `parts`) followed by `done`. If the client disconnects in the small window **after** the delta(s) but **before** `done` is consumed, `finished` is still `False` and the fallback is written to `CoachMessage` with `interrupted=True`. Next turn's context window then feeds that fallback back into the model — the exact contamination **B16** forbids. Narrow race (fallback is short, `done` follows immediately) → Low, but the interrupted path bypasses `is_coach_error_fallback`.

**Fix:** guard the interrupted `_record` with `response_formatter.is_coach_error_fallback(partial)` before persisting (the same check the `done` path already applies).

## A-8 — [Low, NEW] Numeric env parsing crashes boot with a raw traceback

**Files:** `app/config.py` (bare `int(os.getenv(...))` / `float(...)` at `:75,102,106,117-120,129-131,134,137,146-147,173-175,281,333`); `app/services/ai_gate.py:32-40`.

A typo'd value (`AI_MAX_CONCURRENCY=four`, `AI_CACHE_TTL_MACRO=1h`) raises `ValueError` at import → boot dies with a cryptic traceback → health gate rollback. `gunicorn.conf.py` already models the safe pattern (`_positive_int` guard) but `config.py`/`ai_gate.py` don't. Fail-fast is defensible for hard-safety knobs, but TTL/retry knobs shouldn't hard-kill boot.

**Fix:** reuse a guarded parser (fallback-to-default + logged warning) for the non-safety-critical numeric env knobs.

## A-9 — [Low, NEW, likely unreachable] `detect_plateau` strength-threshold mismatch can recommend deload to a progressing user

**File:** `app/services/training_progression/analysis.py:112-120,142`.

`detect_plateau` cancels a plateau on a strength uptrend only when `len(active_s) >= MIN_PLATEAU_WEEKS` (3), but the report's `strength_trend`/`is_progressing` use `series_trend`, which reports "up" from just **2** active values. With exactly 2 strength-active weeks but 4 flat volume-active weeks, `detect_plateau`→True and `detect_deload_due`→True while `is_progressing`→True; `derive_next_signal` precedence then emits **"deload"** despite rising estimated 1RM. Likely unreachable: a window with `total_volume>0` almost always contains a `weight_kg>0, reps>0` entry (→ `best_estimated_1rm>0` → the week is strength-active too), so this only bites when `WorkoutLog.volume>0` rows exist with `weight_kg=0` (e.g. time/cardio volume).

**Fix (defensive):** use the same min-active count in `detect_plateau`'s strength guard as `series_trend` so the plateau/deload and trend layers agree on when a strength series is "active."

## Verified clean (independently re-traced this pass)

- **AuthZ / IDOR:** all 18 blueprints swept — every record loaded by an attacker-suppliable ID is query-scoped to `current_user.id` or ownership-checked after load; `require_auth` re-resolves the user from the verified token `sub` and asserts `resolved.id == current_user.id`. No mass-assignment (explicit field allowlists).
- **Injection / XSS:** no string-formatted/`text()` SQL in `app/`; raw psycopg2 (`coach_context_queries.py`, `fitx_mcp/server.py`) uses `%s` binding; no `pickle`/`yaml.load`/`eval`/`exec`/`subprocess`; zero `|safe`/`Markup`/`render_template_string`; frontend user-content sinks escape or route through DOMPurify.
- **CSRF:** two-layer guard (Origin/Referer + per-session synchronizer token) on all state-changing methods; no state-changing GET; no `sendBeacon`/XHR write path bypassing `X-CSRFToken`.
- **SSRF:** the user-URL fetch surface (`menu_fetch.py`) is strongly hardened — allow/deny lists, port allowlist, per-hop redirect re-validation, DNS-pinning against rebinding, all-A-record checks, size caps; verified against a bypass battery (metadata IP, RFC1918, loopback, CGNAT, NAT64/6to4, IPv4-mapped) — all blocked.
- **Secrets / JWT / cookies:** no secrets logged; `cognito_service._wrap` maps provider errors to a fixed set (no raw leakage); RS256 + iss/aud/exp/token_use validation; secure cookies (`HttpOnly`/`SameSite=Lax`/`Secure`); CSP with per-request nonce, no `script-src 'unsafe-inline'`.
- **File / image / S3:** no `request.files` — all image intake is base64 data-URLs through one choke point (`validators._verify_image_bytes`: MIME allowlist blocks SVG, Pillow `verify()`, pixel-bomb caps); S3 keys are server-generated per-user UUIDs; presigned URLs owner-scoped; credentials from EC2 IAM instance profile, SSE-AES256.
- **Wearables OAuth (new module):** per-provider session `state` validated on callback; token-exchange exceptions masked to a generic 502; Fernet-encrypted tokens with prod key enforced outside debug/test; concurrency-safe `IntegrityError`-retry upserts; explicit 10 s timeouts on all outbound calls.
- **Gamification / ledger atomicity:** `award_xp` column-locked `FOR UPDATE`; rollover autoflushes winner XP before the bulk `weekly_xp=0`; `WeeklyResetLog` UNIQUE idempotency; challenge completion is exactly-once (`WHERE completed_at IS NULL` UPDATE, savepoint-per-challenge, `count_challenge_xp=False` recursion cut); meal ledger `commit_once` resolves the uniqueness race, XP/quests only on `created==True`, zero-macro AI failures return 502 without writing; streak `update_streak` is once-per-Istanbul-day.
- **Time correctness:** no `date.today()`/`utcnow().strftime` day-key bypasses in the ledger/quest paths; readers use `timeutil` + `utc_day_bounds`; trailing `weekly_windows` fix (prior #5) verified applied and consumed consistently.
- **Reliability plumbing:** every outbound HTTP has an explicit timeout; no bare `except:`; RQ `enqueue_or_run` inline fallback sound (no session leak / boot-migration race); Postgres `pool_pre_ping` + `pool_recycle`; graceful degradation for Redis/worker/Bedrock/OpenAI/FatSecret/S3 outages; `LOGIN_FAIL_CLOSED` the one deliberate documented hard-fail.
