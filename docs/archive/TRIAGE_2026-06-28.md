## 🔴 HIGH

### H1 — Diary meal-logging bypasses the macro sanity clamp ✅ verified
- **Files:** `app/blueprints/nutrition/diary.py:182-225` (`diary_add_item`), `:255-285`
  (`diary_update_item`), `:322-348` (`diary_log_meal`)
- **Severity:** High (data integrity)
- **Problem:** Every *other* write path into the canonical `MealLog` ledger now runs values through
  `nutrition_pipeline.clamp_serving_macros`: the override path (`meallog.py:73-92`, the C1 fix from
  the 2026-06-26 triage), `quick_add_meal`, and the suggestion path. The diary path only clamps
  **negatives** to 0 (`max(..., 0)`); it never applies the upper physical-plausibility clamp. All
  per-item macros (`serving_calories`, `serving_protein`, `metric_serving_amount`, `per_100g.*`) come
  straight from the request body, are written to `CustomMealItem`, then summed verbatim into
  `MealLog` by `diary_log_meal`.
- **Impact:** A client can POST e.g. `serving_calories: 90000` and it lands in the canonical ledger
  (the DB `CheckConstraint` only rejects > 100000 kcal). This corrupts daily totals, protein nudges,
  menu "remaining budget", and weekly reports — the exact failure the clamp was added to prevent.
- **Fix:** Run the computed item totals through `clamp_serving_macros` in `diary_add_item` /
  `diary_update_item`, or clamp the meal total in `diary_log_meal` before persisting — matching the
  other ingest paths. (Same single source of truth: `nutrition_pipeline.clamp_serving_macros`.)

### H2 — Unbounded user input length into the LLM on `/ask` (cost/abuse) ✅ verified
- **Files:** `app/blueprints/coach.py:117` ; `app/services/ai_coach.py:1116,1168`
- **Severity:** High (cost/abuse)
- **Problem:** `question` is read with only `.strip()` and passed verbatim into the model message.
  Conversation *history* is capped (`COACH_HISTORY_CHAR_CAP = 400`), but the current question is not.
  With `tool_choice="auto"` and a loop cap of 5, each request can fan out to 5+ model calls, each
  re-sending the full system prompt + context + the giant question.
- **Impact:** An authenticated user can submit a multi-megabyte payload → token-cost amplification /
  bill blowup. The 30/hour rate limit still permits large per-call cost; the (more expensive) Bedrock
  path is reachable here.
- **Fix:** Cap `question` length in the route before dispatch (e.g. `question[:4000]`, return 400 on
  oversize). Pair with H2-related quota work below.

## 🟠 MEDIUM

### Data correctness

#### M1 — Display dates rendered in UTC instead of Istanbul (day shifts near midnight)
- **Files:** `app/blueprints/tracking.py:90` (`progress`), `:192` (`checkin_history`), `:369`/`:404`
  (`history`, `last_session`); `social.py:230,275` (message `HH:MM`); `plan.py:58`;
  `training.py:544` (`created_at` date)
- **Problem:** These call `created_at.strftime("%d.%m"...)` directly on naive-UTC timestamps.
  CLAUDE.md mandates all day/time presentation derive from `app/timeutil` (Istanbul). For a record
  created 00:00–03:00 Istanbul, the rendered `DD.MM` is the previous calendar day; chat timestamps
  are off by the UTC offset.
- **Fix:** Convert via `app_date_of(created_at)` + `display_ddmm(...)` for dates; convert to `APP_TZ`
  before `%H:%M` for message times. (Helpers already exist.)

#### M2 — `meal_history` groups a row-capped result by day → incomplete day totals
- **File:** `app/blueprints/nutrition/meallog.py:247-272`
- **Problem:** Query is `order_by(created_at.desc()).limit(50)` and *then* grouped by `tarih`. If a
  day straddles the 50-row cutoff, that day's `totals` are computed only from rows inside the limit,
  silently undercounting calories/macros for the oldest day shown.
- **Fix:** Cap by number of *days* (subquery of distinct recent `tarih`), or fetch all rows for the
  days being shown rather than a flat 50-row limit.

#### M3 — Activity calories double/triple-count across intensities ✅ verified
- **Files:** `app/blueprints/tracking.py:259-314` (`log_daily_activity`), `:317-340`
  (`today_activity`)
- **Problem:** The idempotency key is `(user_id, date_key, intensity)`. Logging the same steps under
  `light`, then `moderate`, then `brisk` creates three rows, and `today_activity` **sums**
  `calories_burned` across all of them. There is no notion that "today's steps" is one quantity —
  changing the intensity dropdown adds calories instead of replacing.
- **Impact:** Inflated burned-calorie totals (and any energy-balance display) by toggling intensity —
  a correctness bug for honest users and a mild abuse vector.
- **Fix:** Key idempotency on `(user_id, date_key)` (one activity row per day), or have
  `today_activity` take the most-recent/max per day rather than summing across intensities.

### AI / cost-abuse

#### M4 — AI plan quota does not cover the agentic chat / tool loop
- **Files:** `app/blueprints/coach.py:112-142` ; `app/services/premium.py`
- **Problem:** `AI_PLAN_QUOTA_ENABLED` gates plan *generation*, but `/ask` (the most expensive path —
  multi-turn tool loop on Bedrock Sonnet + FatSecret + per-item LLM macro batches) is protected only
  by `AI_RATELIMIT = 30/hour`. A non-premium user gets 30 full agentic conversations/hour with no
  weekly quota.
- **Impact:** Freemium bypass for the costliest feature; cost abuse.
- **Fix:** Apply a quota/credit check (or premium-aware tighter rate limit) to `/ask`, consistent
  with the documented freemium intent.

#### M5 — Broad `except Exception` masks real OpenAI/JSON failures across the nutrition pipeline
- **Files:** `app/services/ai_nutrition.py` (e.g. `:217,281,333,626,780`); `fatsecret.py:659`
- **Problem:** Many LLM/JSON paths catch bare `Exception` and return `{}`/`[]`. This is the intended
  graceful degrade, but it also swallows genuine misconfiguration (bad API key, schema change) into
  "no results," making outages look like empty data.
- **Fix:** Log at `warning` with `exc_info` consistently (some paths already do, e.g. line 783) so
  Sentry sees them.

#### M6 — MCP FatSecret token cache: thundering-herd + unsafe payload read
- **File:** `fitx_mcp/server.py:462-486`
- **Problem:** In `_get_fatsecret_token` the cache *read* is inside the lock, but on miss the lock is
  released, the network fetch happens unlocked, and the write re-acquires the lock — two concurrent
  callers can both fetch. Also `data["access_token"]` will `KeyError` on an OAuth error payload.
  Contrast the hardened app-side copy (`fatsecret.py:38-64`) which holds the lock across the critical
  section and validates the payload.
- **Severity:** Medium (MCP is stdio/in-process per architecture, so blast radius is small) — but an
  inconsistency with the app-side implementation.
- **Fix:** Mirror the app-side `fatsecret.py` locking + payload validation.

### Security / auth (hardening — no Critical/High)

#### M7 — Account-enumeration via `UserNotConfirmedException` on login
- **Files:** `app/services/cognito_idp.py:30-41` ; `app/blueprints/auth.py:216-218`
- **Problem:** Login is timing-equalized and returns generic `bad_credentials` for
  not-found/wrong-password (good), but `UserNotConfirmedException` returns HTTP 403 +
  `needs_verification: True`, letting an attacker distinguish "registered-but-unconfirmed" accounts.
  Mitigated by the per-username rate limit but not eliminated.
- **Fix:** Gate the `needs_verification` hint behind a successful password check, or accept the UX
  tradeoff explicitly.

#### M8 — Per-username rate limit enables targeted account lockout
- **Files:** `app/blueprints/auth.py:63-76,185-186`
- **Problem:** The per-username limit (15 failures / 15 min, keyed on submitted username) protects
  against distributed brute force, but an attacker who knows a username can deliberately burn the
  victim's failure budget → self-healing 15-min lockout. Documented as an accepted tradeoff.
- **Fix:** If lockout abuse becomes a concern, key on IP+username conjunction.

#### M9 — `SESSION_COOKIE_SECURE` keyed off a module-load `_IS_DEV` constant
- **File:** `app/config.py:23,156-159`
- **Problem:** `_IS_DEV` is evaluated once at import, asymmetric with the SECRET_KEY logic
  (`:143-151`) which reads env at call time. If anything sets `FLASK_ENV=development` to bypass the
  SECRET_KEY requirement, it *also* silently disables Secure cookies. Low practical risk (env fixed
  before import).
- **Fix:** Evaluate the dev flag once in `configure_app` and reuse a single value for both decisions.

### Infra / data-layer

#### I-M1 — `db_init.py` runs raw legacy ALTERs + `create_all` + auto-upgrade on every boot
- **File:** `app/db_init.py:9-188`
- **Problem:** Boot path does Alembic `upgrade()` → `create_all()` → ~30 idempotent raw ALTER/UPDATE
  statements → conditional `stamp()`. ALTER-loop failures are swallowed at `debug` level (line 80).
  Race-safety relies *only* on the single-worker invariant (Dockerfile `--workers 1`); scaling
  workers/containers against the same RDS can race concurrent `create_all`/`upgrade`/`stamp`. The
  `UPDATE user_quest_progress SET is_claimed = true WHERE is_claimed = false` (line 48) is a
  full-table write running on **every** boot, masquerading as a schema migration.
- **Fix:** Move remaining raw ALTERs/UPDATEs into proper Alembic migrations (CI already has a drift
  guard, `continue-on-error: true`, waiting for this cleanup), and gate boot-time migration behind an
  explicit one-shot job rather than per-container boot.

#### I-M2 — Migration `f6a7b8c9d0e1` `upgrade()` is an irreversible data drop
- **File:** `migrations/versions/f6a7b8c9d0e1_drop_user_daily_nutrition.py:29-48`
- **Problem:** `DROP TABLE IF EXISTS user_daily_nutrition` with no backup/verification step before
  the drop; `downgrade()` recreates an empty table (dropped data unrecoverable). Intentional and
  preceded by a backfill migration, but it is the one genuine data-loss point in the chain.
- **Fix:** Acceptable as-is given the prior backfill; document the dependency, or add a pre-drop
  row-count assertion.

#### I-M3 — Boot-time error handling / silent schema drift
- See I-M1; the swallowed ALTER failures mean schema drift can go unnoticed until a query fails.

  `app/blueprints/tracking.py:208-256`: if `current_activity`/`goal` unset, TDEE defaults to 1.2 and
  this is written into `last_sess.target_calories`, driving menu "remaining" and protein goals. Guard
  the recompute or surface the fallback.
- **L3 — `friends_search` discloses friendship status of arbitrary users.**
  `app/blueprints/social.py:76-98` returns pending/rejected status of any relationship with the
  searcher — minor privacy leak (only the searcher's own edges; not an ownership violation).
- **L4 — `print()` instead of logger in MCP FatSecret parse errors.** `fitx_mcp/server.py:578,581,583`
  — bypasses logging/Sentry (the anti-pattern fixed elsewhere; see `ai_nutrition.py:781`).
- **L5 — Vision OCR sends up to 4000 output tokens with no per-user cost guard.**
  `app/services/menu_ocr.py:165-180` (`gpt-4o-mini` vision, reachable via Drive images + uploads).

- **L6 — `log_request` logs `X-Forwarded-For` verbatim.** `app/observability.py:59-62` — client-

## ✅ Verified safe (do NOT "fix" these away)

- **SSRF defense** (`app/services/menu_fetch.py:10-117`): IP-class validation, IPv4-mapped unwrap,
  port allowlist (80/443), per-hop re-validation, **DNS-rebinding pin**, manual redirect following,
  size caps. Exemplary. Scanner route is `@login_required` + rate-limited.
- **MCP authorization:** documented "no auth" risk is mitigated — HTTP transport refuses to start
  without `FITX_MCP_ALLOW_HTTP=1` + loopback bind (`server.py:904-910`); in-process path enforces
  identity via `_assert_principal` (`ai_coach.py:120-129`); `user_id` is never taken from LLM args.
- **IDOR / ownership:** diary, supplements, social, S3 key segment-equality (`s3_helper.py:88-96`),
  MealLog/CustomMeal/Friendship loads all scope to `current_user.id`.
- **Gamification integrity:** quest claiming idempotent per day (`uq_user_quest_day` +
  `gamification.py:228-243`); `complete_workout` guarded by `uq_pump_check_day` UNIQUE + full
  rollback (no double XP on TOCTOU); `friend_accept` uses a guarded conditional UPDATE; weekly
  rollover idempotent via `WeeklyResetLog`; leaderboard after_commit/after_rollback avoids Redis
  drift.
- **Zero-macro guard:** AI/parse failure correctly refuses zero rows across `log_meal`,
  `quick_add_meal`, suggestion-accept (note: this is *separate* from H1, which is the missing *upper*
  clamp on the diary path).
- **Secrets / cookies / infra:** no hardcoded keys (AWS via IAM instance profile); FatSecret bearer
  TLS enforced both sides; SECRET_KEY required outside debug; HttpOnly + SameSite=Lax + Secure
  cookies, `session_protection="strong"`, fixation handling; Docker non-root uid 10001, loopback-only
  ports; CI uses OIDC (no long-lived AWS keys); robust truncated-JSON salvage for LLM output;
  Dependabot configured, no known-vulnerable pins.
