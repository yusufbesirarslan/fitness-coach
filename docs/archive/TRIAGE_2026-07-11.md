## Track 1 — Infra / Deploy / Data integrity

### I1 — HIGH (availability): AI gate + scrape gate together consume the entire thread pool
**File:** `app/services/ai_gate.py:27` (`AI_MAX_CONCURRENCY=5`), `:36` (`SCRAPE_MAX_CONCURRENCY=3`); `Dockerfile:43` (`--workers 1 --threads 8`).

**Verified:** two independent bounded semaphores, `5 + 3 = 8`, exactly the gunicorn
thread count. The A1 design (see `ai_gate.py` docstring) deliberately caps AI at 5 of
8 so `/health` and cheap routes keep ≥3 reserved threads. The later scrape semaphore
(3) was added independently and **erases that reserve**: 5 AI requests inside `fn()`
plus 3 concurrent menu scrapes can occupy all 8 threads simultaneously.

**Failure scenario:** under that load `/health` (and every cheap route) waits for a
free thread. Docker `HEALTHCHECK` (5s timeout) fails → container flips `unhealthy`; a
deploy overlapping load can time out the gate and trigger a **spurious rollback** — the
exact failure A1 exists to prevent.

**Fix:** ensure `AI_MAX_CONCURRENCY + SCRAPE_MAX_CONCURRENCY < threads` (e.g. `4 + 2 = 6`,
leaving ≥2 reserved), or share a single semaphore, or move `/health` off the
request-serving path. Add a boot-time assertion/log tying the two caps to the thread count.

### I2 — HIGH (availability): health gate green while login is 100% offline (Redis-down)
**Files:** `app/__init__.py:40-55` (`/health` runs `SELECT 1` only and *deliberately*
does **not** treat `limiter_storage=degraded` as unhealthy — comment at `:40-41`);
`app/blueprints/auth.py:210-214` (login returns **503 for every user** when
`login_throttle_available()` is False, i.e. Redis unreachable, default `LOGIN_FAIL_CLOSED=1`).

**Failure scenario:** Redis crashes / OOM-evicts *after boot* (it runs `maxmemory 200mb`
+ `allkeys-lru` and can restart). `depends_on: service_healthy` only guards cold start.
Docker HEALTHCHECK stays green, the deploy gate (`deploy.yml` curls only the HTTP status)
passes, external monitors see 200 — **yet no one can log in.** CLAUDE.md's A5 note says
"watch the `limiter_storage` field," but nothing actually does.

**Fix:** have the deploy gate / an external probe parse the `/health` JSON and alert/fail
when `limiter_storage == "degraded"`, and/or add a readiness endpoint that fails when
login is fail-closed. This is the operational half of the accepted A5 tradeoff — the
tradeoff is only safe if `limiter_storage=degraded` is actually monitored.

### I3 — MEDIUM: `/health` is too shallow to gate a deploy
**File:** `app/__init__.py:44-55`. The gate proves only that Postgres answers `SELECT 1`.
It does not verify Redis (see I2), the FatSecret proxy (I4), that `BEDROCK_ENABLED` is
truly on (`config.py:189` only logs), or that real routes render — so a deploy that boots,
migrates, and answers `/health` is declared success even if the primary AI path silently
fell back to OpenAI or food search is dead.
**Fix:** add a `?deep=1` / separate readiness endpoint that also pings Redis and reports
degraded subsystems; keep shallow `/health` for the Docker liveness probe.

### I4 — MEDIUM: FatSecret loopback proxy is an unsupervised SPOF
**Files:** `nginx.conf:30-32,88-94` route `/fatsecret/rest/server.api` → `127.0.0.1:3000`,
but nothing in the repo starts, restarts, or health-checks that process (absent from
`docker-compose.yml` and `deploy.yml`). If it dies, all FatSecret calls 502 and macro
resolution silently degrades to LLM guesses (`config.py:195-198`) with no restart/alert.
**Fix:** bring the proxy under a supervisor (systemd unit or a loopback-bound compose
service) with a restart policy, and include it in the deep health check.

### I5 — LOW: `CognitoSession` rows never expired / garbage-collected
**File:** `app/services/session_store.py:50-106`. `create()` inserts a row per login;
rows are removed only on explicit logout or refresh failure. No TTL sweep, no CLI cleanup.
The table grows unbounded and retains expired sessions holding encrypted tokens.
**Fix:** add a periodic cleanup (extend the `weekly-reset` CLI or a cron) deleting rows
past `access_token_exp` + refresh window.

### A2 reminder (still relevant, not a new bug): destructive migrations auto-apply on the health-gated boot
The migration chain is **healthy** — all 21 revisions trace to a single head
`aa11bb22cc33`; the fork at `f6a7b8c9d0e1` is correctly reunited by merge `f8a9b0c1d2e3`;
newest migrations are additive. But `f6a7b8c9d0e1` (`DROP TABLE user_daily_nutrition`) and
`b8c9d0e1f2a3` (`meal_log.tarih SET NOT NULL`) are the destructive pattern CLAUDE.md's A2
warns against; they run on the very boot the health gate judges and are **not** reverted by
a code rollback. Currently safe (the objects were dead a release earlier). Keep future
schema tightening on the two-phase expand/contract path, and gate any unavoidable
destructive migration behind `FITX_DB_AUTO_UPGRADE=0` + a one-shot `flask db upgrade`.

## Track 2 — Security & Authorization

### S1 — MEDIUM: indirect prompt injection via friend-controlled content into the tool-enabled coach
**File:** `app/services/ai_coach.py:260-281`. The `[ARKADAŞ AKTİVİTELERİ]` block injects
other users' `username`/`full_name` and activity `content` into the same conversation that
exposes state-changing tools (`manage_user_memory`, `confirm_and_commit_meal_log`,
`stage/confirm_workout_log`). Attacker-controllable fields include `full_name`
(`profile.py`, ≤150 chars) and activity strings embedding user input (e.g. supplement
`product_name`, `supplements.py:87`).

**Impact (bounded to the victim's own account** — `user_id` is server-bound, no cross-user
read): a malicious friend can set `full_name`/product name to an injection payload; when the
victim opens the coach it rides in context and can attempt to corrupt the victim's stored
memory (injuries/dietary restrictions feed real training/nutrition decisions), log bogus
meals/workouts, or burn the AI-chat quota. There is a defensive fence, but LLM guardrails
are probabilistic. **This is INF-1 from the 2026-07-05 pass, re-confirmed still open.**

**Fix:** don't co-locate third-party text with write-tools — summarize friend context in a
separate no-tools call, and/or hard-require server-side explicit confirmation for `confirm_*`
(the `PendingAction` staging already exists; never let a commit fire from a turn whose only
"approval" came from injected text). Strip/neutralize control tokens more aggressively.

### S2 — MEDIUM/LOW: Cognito token-at-rest key silently derives from `SECRET_KEY`
**File:** `app/services/session_store.py:29-39`. When `COGNITO_TOKEN_ENC_KEY` is unset
(the default), the Fernet key encrypting stored Cognito **access/refresh tokens** is
`base64(sha256(SECRET_KEY))`. Contrast `app/services/wearables/crypto.py:15-22`, which
**raises** unless a dedicated `WEARABLE_TOKEN_KEY` is set outside dev. The wearable-token
design decided key separation matters; the Cognito store does not enforce it — and
`SECRET_KEY` is higher-exposure (it also signs sessions).

**Scenario:** if `SECRET_KEY` leaks, an attacker with DB read can decrypt every stored OAuth
token and impersonate users against Cognito.
**Fix:** enforce `COGNITO_TOKEN_ENC_KEY` in non-dev exactly as `crypto.py` enforces
`WEARABLE_TOKEN_KEY`.

### S3 — LOW: raw internal exception text returned to clients
**File:** `app/blueprints/wearables.py:58` (`f"{provider} bağlantısı kurulamadı: {exc}"`),
`:95` (`f"Senkronizasyon başarısız: {exc}"`), `:109` (`f"WHOOP isteği başarısız: {exc}"`).
Raw `exc` strings can include upstream URLs, library internals, or partial responses.
Elsewhere errors are mapped to safe messages (`cognito_service._wrap`, `menu.py`).
**Fix:** log `exc` server-side; return a generic message.

### S4 — INFO (latent): login reads `sub` from the unverified decode after verifying the token
**File:** `app/blueprints/auth.py:246-254`. `cognito_jwt.validate_token(tokens["id_token"], "id")`
runs, but its **return value is discarded**; the subsequent `claims["sub"] != user.cognito_sub`
check reads `result["claims"]` from the *unverified* `_decode_claims`
(`cognito_service.py:241`). Not exploitable today (same token string was just cryptographically
verified and delivered directly by Cognito over TLS), but fragile — a refactor that reorders
or drops the verify would silently trust attacker-influenced claims.
**Fix:** compare `sub` against the **verified** claims returned by `validate_token`.

> **Verified SOLID (not vulnerabilities):** RS256-pinned JWT validation with
> iss/aud/token_use/exp checks and per-request re-validation; IDOR ownership scoping on
> every by-id route + S3 keys; SSRF DNS-pinning + per-hop re-validation + port allow-list on
> the menu scraper; server-bound `user_id` in the coach tool-loop; two-layer CSRF; per-request
> CSP nonce with no `unsafe-inline`; avatar raster-byte validation (no SVG/HTML); no hardcoded
> secrets (IAM instance profile); parameterized SQL everywhere; MCP HTTP transport gated behind
> `FITX_MCP_ALLOW_HTTP=1` + loopback bind.

## Track 3 — Backend correctness

### B1 — MEDIUM: MCP reports count the synthetic Pump-Check marker as a real exercise
**File:** `fitx_mcp/server.py:751-758` (`generate_weekly_report`, `GROUP BY exercise_name`)
and `:648-652` (`log_workout_entry` today totals). The in-app "D4" contract treats
`WORKOUT_COMPLETION_MARKER = "Antrenman tamamlandı (Pump Check)"` (`app/models.py:505`) — a
synthetic `volume=0` `WorkoutLog` row written by `complete_workout` (`training.py:212-216`) —
as *not a real exercise*, and every in-app aggregation excludes it (`ai_coach.py:411`,
`tracking.py:581`). The MCP server never references the constant (grep: 0 hits).

**Consequence:** for users who complete workouts only via the UI Pump Check (the common
path — the UI writes no per-exercise rows), the coach's `workouts.exercises` breakdown is
entirely this phantom row (volume 0, `entries` = number of Pump-Check completions), and
`today_entry_count` is inflated by 1.
**Fix:** add `AND exercise_name <> 'Antrenman tamamlandı (Pump Check)'` (or import the
constant) to the aggregation queries at `:648-652` and `:751-758`, matching the D4 exclusion.

### B2 — MEDIUM: recovery / overload-stall nudges silently suppressed after any weight update
**File:** `analytics_engine.py:154-161` (`_latest_checkin`), consumed by
`_check_recovery_signals` (`:164`) and `_check_overload_stall` (`:184`). `_latest_checkin`
returns the newest `WeeklyCheckIn` with **no** `yogunluk.isnot(None)` filter. But
`/update-weight` writes **sparse** rows containing only `weight`
(`tracking.py:302` — all of `yogunluk/fatigue/uyku_kalitesi/progressive_overload` NULL).
Everywhere else filters these out (`tracking.py:181-183,244-247,667-668`); analytics does not.

**Scenario:** a real check-in reports `fatigue=5, uyku_kalitesi=2` (should raise
NUDGE_RECOVERY) → user later taps "update weight" → the sparse row becomes "latest" →
`poor_sleep`/`high_fatigue` evaluate against NULL (False) and `progressive_overload` is `""`
(False) → the recovery/deload nudge stops firing until a new full check-in is submitted.
**Fix:** filter `_latest_checkin` with `WeeklyCheckIn.yogunluk.isnot(None)`, consistent with
the rest of the app.

### B3 — LOW: `workout_status` can report "not completed" for a completed workout
**File:** `app/blueprints/training.py:264-275`. Idempotency for `complete_workout` is now
`PumpCheck`-based (`:139-145`, `uq_pump_check_day`), but `workout_status` still derives
completion from a `UserQuestProgress` row for `quest_type="workout_logged"` (written only if
that quest is seeded). In an environment where the quest isn't seeded, a completed workout
(PumpCheck + XP written) still reports `completed: False`, breaking the cross-device "done
today" indicator. Prod seeds it via `seed-quests`, so impact is limited to unseeded envs.
**Fix:** base `workout_status` on today's `PumpCheck` — the same signal as the idempotency guard.

### B4 — LOW: `cleanup-test-users` leaves orphan rows on SQLite
**File:** `app/cli.py:26-42` (`_purge_user`). The manual delete list omits `CognitoSession`,
`PumpCheckLike`, `PumpCheckComment`, and the `Wearable*`/`UserWearableConnection` tables. On
Postgres these are swept by `ON DELETE CASCADE`, but on SQLite (local/test, FK enforcement off
by default) `db.session.delete(user)` won't cascade, orphaning those rows. Admin-only CLI, low
impact.
**Fix:** add the missing child models to the manual deletion loop.

> **Verified SOUND:** day/time handling routes through `app/timeutil` and the MCP server's own

> `with_for_update` (C1 identity-map trap avoided); friend-accept, referral, water,

> unique-constraint upserts against double-award; macro math funnels through
> `clamp_serving_macros`; `premium_ai_plan_gate` keys quota on real `status_code == 200`.
