## 🔴 HIGH

### 1. `diary_log_meal` — double-submit writes duplicate rows into the canonical ledger
- **File:** `app/blueprints/nutrition/diary.py:291-328`
- **Problem:** Check-then-act with no atomic guard:
  ```python
  meal = db.session.get(CustomMeal, meal_id)
  if meal.is_logged:
      return jsonify({"error": "Bu öğün zaten kaydedilmiş"}), 400
  ...
  entry = MealLog(...)        # canonical ledger row
  db.session.add(entry)
  meal.is_logged = True
  db.session.commit()
  ```
- **What goes wrong:** Two concurrent `POST /api/diary/meal/<id>/log` (double-tap on
  "Kaydet", or a retried request) both read `is_logged == False`, both INSERT a `MealLog`
  row, both set `is_logged = True`, both commit → **two identical `MealLog` rows** in the
  canonical ledger. Daily totals, protein nudge, menu consumed/remaining math, and weekly
  reports all double-count. There is no `UniqueConstraint` linking `CustomMeal → MealLog`
  and no `IntegrityError` fallback, so nothing stops the second write.
- **Why it survived prior rounds:** This is the **same check-then-act race class** already
  fixed with conditional `UPDATE ... WHERE` in `friend_accept` (social.py:162),
  `consume_referral` (referral.py:61), and the staged-meal/-workout commits
  (ai_coach.py:444, :543) — this sibling ledger-writing path was simply never converted.
- **Fix:** Atomically claim the meal first, write the ledger row only when a row actually flipped:
  ```python
  updated = CustomMeal.query.filter_by(
      id=meal_id, user_id=current_user.id, is_logged=False
  ).update({"is_logged": True}, synchronize_session=False)
  if not updated:
      db.session.rollback()
      return jsonify({"error": "Bu öğün zaten kaydedilmiş"}), 400
  # then add the MealLog and commit
  ```

### 2. Alembic migration chain cannot rebuild the schema from an empty DB
- **Files:** `migrations/versions/54f2eb195404_baseline...py` (User table, lines 30-56),
  `migrations/versions/a1b2c3d4e5f6_cascade_fks_indexes_check.py:86`,
  `app/db_init.py:35,55-59`
- **Problem:** Columns `referral_code`, `referred_by_id`, `is_premium`, `premium_since`,
  `profile_picture_key` are **never created by any Alembic migration** (verified by grep
  across `migrations/`). They exist only via `db.create_all()` (fresh DB) or the legacy
  idempotent `ALTER`s in `db_init.py`. Worse, migration `a1b2c3d4e5f6:86` runs
  `ALTER TABLE "user" ALTER COLUMN referral_code TYPE VARCHAR(16)` — which assumes the
  column already exists. Running `flask db upgrade` against a truly empty DB (no
  `create_all` first) fails at that ALTER or yields a schema missing those columns.
- **Impact:** The Alembic history is not a source of truth. Any environment that bootstraps
  purely from migrations (new staging DB via `flask db upgrade`, disaster recovery, a
  contributor following the standard Flask-Migrate flow) gets a wrong/broken schema. There
  is no CI test asserting `flask db migrate` yields an empty diff.
- **Fix:** Add the missing columns to a real Alembic migration so the chain is
  self-contained; add a CI check that `FITX_SKIP_DB_INIT=1 flask db upgrade` on an empty DB
  reproduces the model schema and that autogenerate produces an empty diff.

### 3. `menu_fetch._fetch_page` leaks the `requests.Session` (socket/FD leak)
- **File:** `app/services/menu_fetch.py:249` (creation); returns at `:311` with no close on
  any path; retry at `:308` overwrites `resp` without closing the first.
- **Problem:** `session = http_req.Session()` is created but never closed — no `try/finally`,
  and the function returns the live `resp` while the Session's connection pool stays open.
  On the 403/short-body retry path the first result is replaced without closing.
- **Impact:** Menu scraping is user-triggered; each scrape leaks a pooled connection / FDs
  in the single gunicorn worker. Under repeated use (especially origins that 403 then retry)
  this accumulates and can exhaust file descriptors.
- **Fix:** Copy out the materialized bytes (`resp._content`) and `session.close()` in a
  `try/finally` before returning.

## 🟠 MEDIUM

### 4. `respond_suggestion` accept — double-submit double-logs a suggested meal
- **File:** `app/blueprints/social.py:308-346` (accept branch) + `_process_meal_suggestion_accept`
- **Problem:** Check-then-act on `msg.message_type` with no atomic guard:
  ```python
  if msg.message_type not in ("suggestion_meal", "suggestion_workout"):
      return ...
  if action == "accept":
      msg.message_type = msg.message_type + "_accepted"
      nutrients = _process_meal_suggestion_accept(msg)   # adds a MealLog row
  db.session.commit()
  ```
- **What goes wrong:** Two concurrent accepts both see `message_type == "suggestion_meal"`,
  both append `_accepted`, both run the accept pipeline → **two MealLog rows + two reply
  Messages** for one suggestion. No `UniqueConstraint` on `Message`, no conditional update.
  (Lower severity than #1 — requires the user double-clicking accept on their own suggestion.)
- **Fix:** Atomically claim the transition before side effects:
  ```python
  claimed = Message.query.filter_by(id=msg.id, message_type=msg.message_type)\
      .update({"message_type": msg.message_type + "_accepted"}, synchronize_session=False)
  if not claimed:
      db.session.rollback()
      return jsonify({"error": "Bu öneri zaten yanıtlandı."}), 400
  # then run the macro pipeline / MealLog write
  ```

### 5. `save_nutrition_plan` has no rollback on commit failure → session poisoning
- **File:** `app/blueprints/nutrition/plan.py:30-38`
- **Problem:** `NutritionPlan...delete()` + `db.session.add(new_plan)` + `db.session.commit()`
  with no `try/except`. If `commit()` raises, the exception propagates and the session is
  left in a failed state.
- **Impact:** With a single gunicorn worker reusing the session, the next request can hit
  `PendingRollbackError`/`InvalidRequestError` (cascading 500s) until reset.
- **Fix:** Wrap in
  `try/except Exception: db.session.rollback(); return jsonify({"error": "Plan kaydedilemedi."}), 500`.

### 6. `quick_add_meal` uses raw `float()` on LLM plan macros instead of `_to_float`
- **File:** `app/blueprints/nutrition/diary.py:64-68` (and unguarded `json.loads(plan_record.plan_data)` at `:55`)
- **Problem:** Every other macro read in this file uses the `_to_float` helper, but
  `quick_add_meal` casts `float(meal.get("kalori", 0))` directly. `meal` comes from
  `NutritionPlan.plan_data` (LLM-generated JSON saved verbatim with no validation). A
  non-numeric macro (e.g. `"~30g"`) raises `ValueError`.
- **Impact:** Unhandled `ValueError` → HTTP 500 on the "quick add from plan" write path; the
  user can never add that meal. Corrupt stored plan JSON would also 500 at the `json.loads`.
- **Fix:** Use `_to_float(...)` for all four macros; guard `json.loads` at `:55`.

### 7. `log_meal` override-macros path bypasses `clamp_serving_macros`
- **File:** `app/blueprints/nutrition/meallog.py:78-98`
- **Problem:** The `override_macros` branch writes user-supplied macros straight to
  `MealLog` with only `_to_float` + round — no `nutrition_pipeline.clamp_serving_macros`:
  ```python
  override = data.get("override_macros")
  if override and isinstance(override, dict):
      nutrients = {"kalori": round(_to_float(override.get("kalori", 0)), 1), ...}
      entry = MealLog(... kalori=nutrients["kalori"] ...)
  ```
- **What goes wrong:** Same gap the AI-coach staged-commit path was fixed for. Every other
  ledger-writing path clamps physically-impossible values, but this override path does not.
  A client posting `override_macros` of e.g. 3000 kcal lands an implausible row; the DB
  CHECK only catches gross overflow (≤100000 kcal), not "3000 kcal" garbage.
- **Fix:** Route the override through `nutrition_pipeline.clamp_serving_macros(...)` (or the
  local `_sanitize_meal_macros` helper in `diary.py`) before building the `MealLog`.

### 8. FatSecret search swallows token/network failures with no log (silent outage)
- **File:** `app/services/fatsecret.py` — `_food_search_fatsecret` token-acquisition and
  search-request `except Exception: return None` blocks.
- **Problem:** Unlike sibling functions (`_food_get_servings`, `_fs_search_foods`) which
  log, these two blocks return `None` silently. A FatSecret outage or expired credentials is
  invisible; the app falls through to static/LLM macro estimation with no operator signal.
- **Impact:** Macro quality silently degrades app-wide with no alert.
- **Fix:** Add `current_app.logger.warning(..., exc_info=True)` in both blocks.

### 9. Deploy has no rollback and the smoke check does not gate success
- **File:** `.github/workflows/deploy.yml:32-33`
- **Problem:** `git reset --hard origin/main && docker compose up -d --build` with no prior
  image retention. The final `curl -sI /login` (`:33`) output is printed but never asserted —
  job success depends only on SSM command status, not on the app serving 200. A commit that
  builds but boots unhealthy is deployed and left live.
- **Fix:** Keep the prior image tag and roll back on a failed smoke check; make the
  `curl /login` (and `/health`) status code gate the SSM command's exit.

## 🟡 LOW

### 10. MCP server token-refresh uses `data["access_token"]` without an error guard
- **File:** `fitx_mcp/server.py:483`
- **Problem:** The main app's `fatsecret.py` was hardened to check for an `error` field
  before accessing `access_token`; the MCP server still does
  `_fs_token_cache["token"] = data["access_token"]` directly. It runs inside a caller's
  `try`, so it surfaces as a generic error string rather than crashing, but it does not
  mirror the main-app guard. Low because MCP is loopback/stdio-only.
- **Fix:** Mirror the main-app guard (check for `error` in the response payload first).

### 11. `diary_add_item` writes client macros to `CustomMealItem` without clamping
- **File:** `app/blueprints/nutrition/diary.py:163-203`
- **Problem:** Per-100g/serving macros are stored unvalidated; when the meal is later logged
  they reach `MealLog`. Affects only the user's own totals — data-quality, not a security
  boundary. Related to #7 — both stem from un-clamped client-supplied macro entry points.
- **Fix:** Apply the same clamping helper used on the other ledger paths.

## Operational / informational (not new, not exploitable)
- **Single gunicorn worker is load-bearing.** In-memory `_last_rollover_check` state
  (hooks.py:147-159) and the in-memory limiter fallback assume one worker. Scaling >1 worker
  would weaken the rollover throttle and distributed rate-limit accounting. Documented in
  prior triage; flagged again as a scaling pre-condition.
- **`cognito_idp._decode_claims` (cognito_idp.py:170-185) does not verify the JWT
  signature** — acceptable as written because the token comes directly from Cognito over TLS
  via the app's own `initiate_auth` call, not from user input.
