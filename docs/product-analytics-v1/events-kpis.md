# Event contract and KPI definitions

## Closed contract, schema 1

`catalog.json` is the reviewed name/property/source allowlist, copied byte-for-byte to both repos. Dart's immutable enum/schema representation is parity-tested against its copy. Any addition, property meaning change or destination metadata change needs contract review in both repos. Breaking semantics require v2; no wildcard event names or arbitrary dictionaries.

An input envelope has exactly `schema_version` (integer 1), `event_id` (random UUIDv4), `action_id` (random UUIDv4), `name`, `source` (`client` or `server` as fixed by catalog), `occurred_at` (UTC ISO8601), and `properties` (exact required key set). All properties are enum tokens. No optional free text, numbers, nested objects or null properties. The receiver's adapter sets trusted source; a client can never supply server authority. A client JSON `subject`, owner or consent field is rejected.

The gateway obtains the pseudonymous subject and consent generation from its independent authenticated analytics authority. These are routing metadata, not arbitrary client fields. Gateway-generated `received_at` is UTC; environment is destination/project partition, not caller input. Version/build/platform may only be introduced by a later reviewed envelope version; no implicit SDK/device properties. Size cap for future ingress: 2 KiB/event, batches at most 20 events/40 KiB, body logging off; reject extra keys before enqueue.

Never include messages, prompts, responses, photographs/filenames/URLs, nutrition contents/names/barcodes, body measurements, injuries, email, account IDs, Cognito sub, credentials, IPs, raw paths, request/job IDs, domain idempotency keys, stack traces, precise location, device/ad identifiers, or health/refusal inference. Allowlisting rejects sensitive data rather than attempting generic redaction.

## Trigger table

All names below have the prefix `axis_v1_`. Events are proposals unless explicitly identified as existing no-op legacy events in the inventory.

| Name(s) | Source / exact trigger | Properties / frequency |
|---|---|---|
| analytics_enrolled | Server: first admitted independent analytics grant; regrant creates a new subject and a new enrollment | `cohort=new_user|existing_user`; once/grant. `new_user` only if grant within 24h of canonical registration and before onboarding completion, any plan or successful Coach turn. Existing/pre-consent completions never backfilled. |
| app_opened, app_resumed | Client: foreground authenticated analytic session after valid grant; cold start vs background-to-foreground transition | None. One open/process; resume only after >=30 seconds background. No background timer events. |
| screen_viewed | Client: committed visible route changes, after authority; map routes to coarse allowlisted screen | `screen=today|plan|plan_create|coach|workout|nutrition|nutrition_plan|progress|onboarding|settings`. Map serving/manual/search to nutrition, all workout details to workout; sensitive Pump Check/result/detail routes excluded. No query/extras/route title; suppress rebuilds and repeated same visible screen. |

| feature_recovered | Server: success for an action with an earlier confirmed failed attempt | `feature`; same action_id as failed attempt, distinct event_id; same event on replay. A client-only timeout followed by success is separately queried as observed recovery, without inventing authoritative failure. |

Abandonment is derived, never transmitted as a fabricated terminal event: an onboarding attempt started with no completion after 24h is `no observed completion`, finalized after another 24h delivery watermark. Withdrawal/deletion/collection outage censors the attempt; it is not product abandonment. Onboarding retry after 24h is a new attempt, linked only by same still-authorized subject. No missing-health-permission analytics events.

## Identity, time and deduplication

Random subject UUIDv4 per account/environment/grant, issued only after analytics opt-in; mapping stays in the first-party authority with restricted access. Stable across devices only while that grant is active, so retention has an account denominator. No hash of email/account id, no install/device ID. Logout clears local subject, queue and dedup cache; same account can retrieve its still-valid server subject after fresh authentication. Account switch must clear before adopting new principal. Withdrawal/regrant rotates subject, never aliases old vendor identities. Do not claim pseudonymous data are anonymous.

`action_id` is a fresh random analytics-only logical operation ID. Never reuse application idempotency keys. The future authority binds it to verified owner, feature and grant generation. Client intents and server success share it only through validated ownership; server-only actions receive an independently minted internal action ID. Each `(subject, event name, logical transition)` has a stable random event_id in a future receipt; retries reuse the identical ID/timestamp. Gateway uniqueness `(environment, subject, event_id)` and action receipts prevent duplicated success across workers/restarts. Conflicting reuse drops the analytics event with a fixed error counter. No global exactly-once claim for the memory prototypes.

Server events use authoritative commit/completion time. Clients preserve original UTC occurrence time through retries; Ingress rejects timestamps more than five minutes ahead of receipt time. Occurrences older than 24 hours are also rejected; receipt time never silently replaces occurrence time. Device clocks outside that bound are excluded from time-based cohorts, counted only in fixed aggregate quality counters if separately approved. Accepted late events update the proper occurrence date, not receipt date. Ingest delay allowance = 24h; reporting finality is end of metric window +24h. Store both occurrence/receipt in a future approved sink. All dashboard date boundaries use IANA `Europe/Istanbul`, half-open midnight intervals; storage and comparisons use UTC instants, never device timezone. No user timezone collected.

## Eligibility and denominators

Pilot population: consenting adults on supported future analytics builds, collection enabled, non-test accounts in the production project, independent grant valid throughout the evaluated observation window. Test/staging/internal accounts are isolated by destination and enrollment eligibility, never guessed from behavior. Refusers remain fully functional and are excluded from person-level analytics. Report consented/enrolled sample size and collection uptime next to every KPI; these are not statistics for all first 100 users. Pre-existing users use `cohort=existing_user`, never mixed into new-user activation.

`t0` = first `analytics_enrolled` for a new_user subject. `C0` = Europe/Istanbul calendar date of t0. An eligible activation cohort requires continuous analytics authorization/observability through t0+7*24h plus delivery watermark. Withdrawn/deleted subjects are removed from retained identifiable data and reports recomputed; report only approved aggregate counts of exclusions, never interpret them as churn. Published counts can change after deletion. Regrant subjects belong to a returning enrollment cohort, not a newly acquired user; authority must enforce that without forwarding the old subject.

| KPI | Exact definition |
|---|---|
| Observed activation within 7 days | Numerator: distinct eligible new_user subjects with authoritative onboarding_completed, training_plan_succeeded and coach_interaction_succeeded, in any order, between t0 inclusive and t0+7*24h exclusive. Denominator: all eligible new_user enrollees whose complete 7-day window +24h has elapsed. No substitution of login or provider usage. Pre-consent success never reconstructed; users with prior relevant completions are existing_user at enrollment. |
| Time to first value | Median/p75 of first training_plan_succeeded minus t0 among successes; separately first Coach success minus t0. Show numerator and non-success fraction to avoid survivor bias. |
| Signup funnel conversion | Distinct authorized signup attempts resulting in signup_completed / distinct signup_started attempts, within 24h, with full +24h watermark. User conversion additionally distinct subjects. Currently N/A because pilot enrolls after auth. Do not impute signup_started from app_opened or manufacture retrospective completion events. A separately approved aggregate functional signup count may be shown with its own purpose/legal review and no join; it is not a person-level conversion denominator. |
| Onboarding completion | Eligible enrolled subjects starting onboarding who complete within 24h / eligible enrolled subjects starting onboarding with full 24h+24h window. Step conversion uses each prior step's eligible unique attempts. |
| Meaningful activity set M | Authoritative training_plan_succeeded, coach_interaction_succeeded, workout_completed, food_log_succeeded, nutrition_plan_succeeded. Screens, opens, retries, failures, workout_started and enrollment alone do not count. Daily/weekly activity is derived; no additional heartbeat/daily-active event. |
| Meaningful DAU / WAU | Distinct authorized subjects with >=1 M on a complete local date / Monday-Sunday local calendar week respectively. Rolling WAU, if shown, is explicitly last 7 complete local dates and not compared as calendar WAU. DAU/WAU ratio uses matching ending complete date's trailing-7-day denominator. |
| D1/D7/D30 exact-day retention | Numerator: subjects with >=1 M on local date C0+N. Denominator: all new_user enrollees from C0 eligible and observable from t0 through the end of target date, whose target date +24h watermark has elapsed. N in {1,7,30}. No rolling-return interpretation and no immature cohorts as zero. Report target-date windows and eligible n. |
| Activated-user retention (secondary) | Same exact-date formula, but cohort date is date of activation and denominator is fully observed activated subjects. Label separately; never compare directly with enrollment retention. |
| Inactive 7 / inactive 30 | At local date boundary D, previously meaningfully active subjects continuously observable over [D-N days,D), with first M before that interval and zero M during it. Denominator for inactivity rate: all previously active, continuously observable subjects with first M before that interval. Newly enrolled without any M are unactivated, not inactive. |
| Reactivated | First M on date D after >=7 complete consecutive local dates with no M, among previously active continuously observable subjects. Example: last M Monday, no M Tuesday-Monday, return Tuesday qualifies. Weekly reactivation rate = distinct subjects inactive7 at start of week who return during week / inactive7 subjects at week start, continuously observable through week end; separately count newly inactive returners outside that fixed denominator. |
| Nutrition adoption | Distinct eligible enrolled subjects with food_log_succeeded or nutrition_plan_succeeded within 7*24h of t0 / all eligible enrolled subjects with fully observed 7-day+24h window. Existing-user adoption reported separately. |
| Failure/recovery | Unique attempted action_ids with client visible failure / unique client intent action_ids, same feature and complete day; server failure rate uses corresponding canonical server action receipts and is separate. Recovery within 24h = failed action_ids with same-feature success within 24h / failed action_ids with fully observed 24h+watermark. Do not subtract failed client timeouts from committed success totals. |

Founder interpretation for first 100: show counts as `x/n` beside percentages; suppress comparative claims for n<10. Missing consent, weak coverage or immature D30 means unavailable/immature, not poor retention. No collection before grant; no backfill; no contact/re-engagement campaigns from these pseudonyms.
