# Backend and mobile implementation plan

## Source delivered in these draft PRs

Backend: `app/services/product_analytics.py` loads the closed reviewed catalog, rejects unknown envelopes/properties, rejects client assertions of server success, validates UTC time/UUIDs, checks an independent grant port before enqueue/drain, snapshots immutable property values, isolates grant/account transitions, bounds memory/retries/TTL and catches delivery/authority errors without logging payloads. `PRODUCT_ANALYTICS_ENABLED=False`. No application module imports it. `tests/test_product_analytics.py` uses synthetic grants and sinks only. No boto3/AWS, SDK, route, persistence, configuration or feature-flag changes.

Mobile: `lib/core/analytics/product_event_catalog.dart` contains immutable reviewed event/source/property enums; `product_analytics_buffer.dart` accepts only typed client events and independent grants, rejects raw IDs/stale time, bounds an in-memory queue and retries, suppresses duplicates, and clears pending work across account/grant changes, including failed asynchronous delivery. `productAnalyticsEnabled=false`. No application imports it; `NoOpAnalyticsService` remains the active composition. It intentionally does not implement the old `AnalyticsService`: silently adapting old confirmed-response events to authoritative server events would produce false data. No SDK/native project/build version/pubspec changes.

Both: catalog + inventory/KPI/privacy/dashboard design docs. Memory buffers are review/test primitives, not production event storage. Constructor enablement and fake authority/sink injection exist for tests; there is no runtime setting enabling them. Neither prototype establishes real consent, validates a server producer's commit receipt, mints IDs, authenticates a network request, provides multi-worker durable dedup, enforces network timeout or performs provider deletion. Those are explicit follow-up implementation gates below.

## Backend follow-ups after separate source/storage authorization

1. Implement separate analytics decision authority and owner/grant mapping, versioned notice digests, unknown/refuse/withdraw behavior, generation locking and erasure state. Reuse architectural patterns from health consent without sharing its purpose, tables, flags or generations. Fail closed on unavailable authority. No migration in current PR.
2. Approve an authenticated first-party ingress with exact envelope and size limits; server selects source, subject and environment. Verify action ownership rather than accepting a client action UUID as authority. Add independent rate limits and no-body-logging policy. Client can submit intent/view/failure only; server producers are internal ports.
3. Add durable analytic action/event receipts and unique constraints. Isolate analytics writes from domain transactions: after committed result, best-effort nonblocking enqueue may drop on failure; never roll back or delay domain success. If a future transactional outbox is chosen, its availability/failure impact must be explicitly approved. Do not open new network work in request threads. Lost enqueue is reported as an aggregate data-quality limitation, not reconstructed later from content.
4. Add producers at reviewed canonical boundaries: signup `blueprints/auth.py:register` commit; onboarding `services/account_profile.py:complete_onboarding`; first plan `services/mobile_training_generation/service.py` persistence result; Coach `blueprints/mobile_coach.py:_send_authorized_turn` only after non-fallback final authorization and response projection, covering `recorded_turn=None` using a durable success receipt; workout `services/workout_session/service.py` + completion service terminal commit; food `blueprints/food.py` / canonical diary service commits; nutrition plan `blueprints/mobile_nutrition_closure.py` canonical service. Share canonical producer between web/native rather than emitting twice. Exact post-commit placement and authority serialization need integration review; no hooks are added here.
5. Send only reviewed product events through approved adapter: PostHog EU or approved first-party storage. Grant must remain current at dispatch under distributed serialization. Map UUIDs and UTC timestamps exactly, disable profiles/GeoIP/extra enrichment, classify failures by closed enum. Test duplicate retries across workers/restarts and grant changes in flight before enabling.
6. Integrate erasure and retention, deletion status reconciliation, restore-time tombstone replay, access restrictions and aggregate dashboard queries. Never export AI-USAGE subject IDs, messages or functional record bodies. Stop at existing staging role/region access boundary; no production identity is authorized.

## Mobile follow-ups after separate privacy/source authorization

1. Build independent, optional EN/TR analytics settings/opt-in flow and versioned grant repository. Bind a verified grant to the authenticated account + origin + session generation. Do not reuse `AnonymousAnalyticsId` or hash account IDs. Clear queued events synchronously before logout/account switch/deletion/withdrawal. Each operation callback carries its initiating grant token, so an old-account callback cannot record under the new account.
2. Compose facade only when both reviewed source gate and live server grant allow it; keep no-op on unknown state, failure and all existing builds. Add a genuine kill switch separate from AI/health flags. Treat review constructor seams as test-only, never a remote-config opt-in.
3. Add UI intent, route and coarse onboarding milestone hooks outside rebuilds. Do not add new client success hooks for server events. Use account/session-bound analytics-only action IDs; existing functional retry/idempotency keys remain untouched. Move no workout/Coach/auth boundary to serve analytics.
4. Implement first-party transport with explicit timeout/backoff/batch/foreground limits from the architecture spec; inject it so app work never awaits it. Keep offline events in memory, never disk, for launch. Drop expired events and new events when bounds are reached. On withdrawal stop locally immediately even offline; server must refuse stale grants independently.
5. Qualify on physical iOS devices: refused consent zero traffic, no automatic SDK metadata, logout/account callbacks, failed network with functional success, cold start/resume navigation, relative battery/network/startup costs. Then qualify a future binary and its privacy disclosures with founder approval. No build/upload/ASC actions in this task.

## Verification and review boundaries

New tests cover consent refusal and wrong-purpose grant, opt-out/regrant, sensitive-property minimization, client/server authority separation, immutable event snapshot, invalid IDs/time, grant/account isolation, duplicates, queue capacity/expiry, capped failed-network retries and unwired defaults. Mobile also covers account transition during delayed network failure and contract parity; existing no-op analytics wiring and workout/training checks remain intact.

These are focused local checks, not a full launch regression, production network measurement, distributed consistency proof, legal approval or real vendor integration test. See `verification.md` for executed commands/results. Merge and deployment are held even if CI is green.
