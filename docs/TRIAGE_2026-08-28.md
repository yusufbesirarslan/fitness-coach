# Codebase Triage — Needed Fixes (2026-08-28)

Triage produced by three parallel deep-dive reviews of the fitness-coach codebase:
**Security vulnerabilities**, **correctness bugs**, and **architecture / data-integrity /
operations**. Each finding was verified against the actual source (`file:line`), not
inferred from docs.

## Executive summary

The codebase is unusually well-hardened. Across all three reviews **no verified
Critical or High-severity, exploitable/data-loss defect was found.** The heavy-emphasis
subsystems — JWT/auth contract, CSRF, SSRF guards, IDOR/ownership scoping, the AI
streaming provider-fallback (B-rule), workout completion/session state machines, plan
mutation & coach plan tools, training history/progression, and the Alembic migration
chain — are defensive, documented, and pinned by regression tests.

What remains is a set of **Medium / Low residual fragilities, accepted tradeoffs, and
observability/latency issues**. They are listed below, grouped and ranked so they can be
scheduled rather than fought. Nothing here is a fire.

Severity legend: 🔴 Critical · 🟠 High · 🟡 Medium · ⚪ Low · ℹ️ Accepted tradeoff / note

## Priority fixes (worth scheduling)

### F1 · 🟡 Erasure/cascade guard only detects FK columns named `user_id`
- **Where:** `tests/test_cascade_delete.py:39-52`; hand-handled columns in `app/cli.py:161-223`.
- **Problem:** The guard test introspects mappers and flags any class with a column
  literally named `user_id` that is missing from `app/cli.py:_user_child_models`.
  User-referencing FK columns under *other* names — `Notification.actor_id`,
  `Friendship.sender_id/receiver_id`, `Message.sender_id/receiver_id`, `FeedItem.ref_id`
  — are invisible to it (they happen to be hand-handled today).
- **Failure scenario:** A future model adds a second user FK under a non-`user_id` name
  (e.g. `reporter_id`, `mentioned_user_id`). The test stays green, `_purge_user` never
  deletes those rows → orphaned rows after account deletion / GDPR erasure, or (on
  Postgres without a matching `ondelete`) `db.session.delete(user)` fails on the FK.
- **Fix:** Extend the test to enumerate *all* FK columns whose `referred_table == "user"`
  (via `mapper.columns[...].foreign_keys`), and assert each is covered by the child-model
  loop or by an explicit allowlist of hand-handled columns.

### F2 · 🟡 Fresh-DB boot seeds data before the post-stamp Alembic upgrade
- **Where:** `app/db_init.py:64-146`.
- **Problem:** On a brand-new DB the order is `create_all()` → seed (multiple independent
  commits) → `stamp("aa11bb22cc33")` → `upgrade()`. If `upgrade()` raises, seed rows are
  already committed and the version is stamped, leaving a partially-migrated + already-seeded
  state. It is recoverable on next boot (resumes `upgrade()` from the stamp), but the window
  is a real partial state and seeding sits outside the migration transaction.
- **Latent coupling:** Stamping the *fixed* revision `aa11bb22cc33` assumes every migration
  ≤ that point is fully reproduced by `create_all` or is pure data. Holds today (the only
  migration-authored CHECK `ck_meal_log_macro_bounds` is mirrored in `app/models.py:583-588`;
  the only trigger `bb22cc33dd44` sits *after* the stamp so it runs), but silently breaks if
  anyone edits a pre-stamp migration to add a non-model DB object (trigger/partial index/function).
- **Fix:** Move seeding to *after* the stamp+upgrade block; add a CI assertion that no
  migration with `revision ≤ aa11bb22cc33` creates DB objects absent from model metadata.

### F3 · 🟡→⚪ Daily maintenance sweeps run inline on a request thread
- **Where:** `app/hooks.py:283-299` (`maybe_weekly_rollover`, a `before_request` hook),
  gated by the once-per-day NX lock at `hooks.py:252-266`.
- **Problem:** `session_store.purge_expired()`, `mobile_auth.purge_expired()`, and
  `notifications.purge_old()` run directly in the request path. With one worker / 8 threads,
  one unlucky request per day absorbs multi-row DELETE latency and ties up a thread.
- **Fix:** Enqueue these sweeps to RQ (`app/jobs` already exists), keeping the NX lock as
  the scheduler.

### F4 · 🟡 Streaming turns under-report token usage across multi–tool-call loops
- **Where:** `app/services/ai_stream.py:263` — `usage = _usage_of(final) or usage`.
- **Problem:** In a coach turn where Bedrock makes N model calls (read-only tool → final
  answer), each `messages.create` bills tokens, but `usage` is **overwritten** each
  iteration; only the last call survives. The `done` event's `usage`, the CloudWatch token
  metrics (`_emit_metrics("stream", ...)`), and `memory_manager.record_turn`'s persisted
  `prompt_tokens`/`completion_tokens` all undercount tool-using turns. The blocking path
  reports no usage at all, so the two paths are also inconsistent.
- **Impact:** Accounting/observability only — no user-facing incorrectness.
- **Fix:** Accumulate a running sum of `_usage_of(final)` across loop iterations instead of
  replacing.

### F5 · 🟡→⚪ Worker-less streaming gates the terminal `done` frame behind a summarize LLM call
- **Where:** `app/services/ai_pipeline.py:235-243` — `deferred_summarize()` runs *before*
  `yield {"type": "done", ...}`.
- **Problem:** When no RQ queue is configured **and** the unsummarized backlog exceeds
  `AI_SUMMARY_TRIGGER_TOKENS`, the summarize call runs inline right before `done`. All delta
  text has streamed, but the terminal frame (client uses it to stop the spinner/finalize UI)
  is withheld until a blocking `gpt-4o-mini` summarize returns/times out — potentially seconds.
- **Fix:** Emit `done` first, then run the deferred summarize via a background thread or
  `response.call_on_close` on the streaming Response (mirroring the blocking path), so the
  terminal frame is never gated on an LLM call.

## Lower priority (defense-in-depth, latency, observability)

### F6 · ⚪ `full_name` has no charset validation — latent stored-XSS surface
- **Where:** `app/blueprints/profile.py:124-125` (only a `len > 150` check), vs. `username`
  which is restricted to `[A-Za-z0-9_.-]` in `app/services/validators.py:204-219`.
- **Problem:** `full_name` is third-party content shown to other users (`templates/chat.html:33`,
  feed cards, `templates/edit_profile.html:38`) and accepts arbitrary characters including
  `< > " '`. **Not currently exploitable** — every traced sink escapes it (Jinja
  auto-escaping with no `|safe`; `esc()`/`escapeHTML()` in client JS). The protection rests
  entirely on no developer ever missing an escape, with no input-side backstop.
- **Fix:** Apply a charset/blocklist to `full_name` on save (reject `< > " ' &` / control
  chars), mirroring `validate_username` but more permissive.

### F7 · ⚪ Deep health check makes a synchronous outbound HTTP call on the worker thread
- **Where:** `app/__init__.py:234-242` — `/health?deep=1` issues `requests.get(FATSECRET_BASE_URL…, timeout=3)`.
- **Problem:** A slow/hung FatSecret proxy adds up to 3s to every deep probe; an aggressive
  readiness/deploy-gate poller during an incident can pin worker threads on this call. It is
  informational (non-gating) and bounded by `timeout=3`.
- **Fix:** Move the FatSecret reachability check to the background capacity sampler; have
  deep-health read the last cached result.

### F8 · ⚪ Runtime `ThreadReserve` gauge can over-report reserve
- **Where:** `app/services/ai_gate.py:88-99` (`capacity_snapshot`) vs. `blocking_thread_ceiling()`
  at `ai_gate.py:255-266`.
- **Problem:** `thread_reserve = WEB_THREADS - ai_active - scrape_active` excludes
  `model_active`. Correct when model permits nest inside route/`blocking_concurrency_slot`
  permits, but when `AI_MODEL_MAX_CONCURRENCY > AI_MAX_CONCURRENCY` and model slots are
  acquired outside a route gate, the published `ThreadReserve` reads higher than the true
  reserve — a monitoring blind spot exactly at saturation. No request is dropped.
- **Fix:** Subtract `max(0, model_active - ai_active)` in the gauge, mirroring the ceiling math.

### F9 · ⚪ Hydration nudge divides by a fixed 7-day denominator
- **Where:** `app/services/analytics_engine.py:225-226` — `days = 7; avg_cups = sum(...)/days`.
- **Problem:** A user who logs water on only 3 of 7 days at 8 cups each (24 total) computes
  `avg_cups ≈ 3.4 < 6` → `NUDGE_LOW_HYDRATION` fires despite exceeding goal on every tracked
  day. The module already silences the no-rows case, so intermittent-but-adequate loggers
  fall into a misleading middle, conflicting with the "no false positives" intent.
- **Fix:** If per-tracked-day average is intended, divide by `len(rows)`; if a true weekly
  average is intended, change the copy to "you logged water on N of 7 days."

### F10 · ⚪ `_settle()` swallows all exceptions silently
- **Where:** `app/services/plan_confirmation/service.py:220-230` — bare `except Exception: pass`
  around read-transaction rollback cleanup.
- **Problem:** Best-effort cleanup is acceptable, but a persistent failure here is invisible.
- **Fix:** Log at debug level instead of swallowing.

### F11 · ⚪ (latent) `premium_ai_plan_gate` refunds on any non-200
- **Where:** `app/services/premium.py:193`.
- **Problem:** Treats any non-200 as failure-and-refund. Current gated routes
  (`/training-plan`, `/nutrition-plan`) return 200 on success, so it is **not triggered
  today**; but a future gated route returning 201/204/3xx on success would refund a consumed
  allowance.
- **Fix:** Gate the refund on an explicit failure classification rather than `!= 200`, or
  document the 200-only contract at each call site.

## Accepted tradeoffs / notes (no action required)

- **ℹ️ Login user-existence oracle** via `UserNotConfirmedException` (`app/blueprints/auth.py:428-430`):
  narrow account-enumeration signal, only after a correct password, throttled by per-username
  rate limit; usernames already discoverable via friend search. Deliberate UX tradeoff.
- **ℹ️ JWKS forced-refresh cooldown** (`app/services/cognito_jwt.py:115-122`): can transiently
  reject a just-rotated `kid` for up to `JWKS_FORCED_REFRESH_COOLDOWN_SECONDS` (60s). Correct
  DoS mitigation; Cognito keeps signing with the old key during rotation, so impact is bounded.
- **ℹ️ CSP** retains `style-src 'unsafe-inline'` (legacy fallback) and a wildcard
  `https://*.googletagmanager.com` (`app/hooks.py:65-70`). The `<script>`/`<style>` element
  vector is nonce-locked and `script-src-attr 'none'` blocks inline handlers; residual risk is
  `style="…"` attribute injection + trusting Google's GA host set. Long-term: drop the style
  fallback and pin GA hosts.
- **ℹ️ `db_init` runs `lb_rebuild()` + referral backfill on every boot** and `before_request`
  hooks carry maintenance sweeps + per-user `SELECT … FOR UPDATE` streak logic. Each is
  idempotent / NX-locked / race-correct, but collectively they load boot and request hot paths
  with work a worker lane would carry more cleanly.

## Structural assessment (from the architecture review)

Mature Flask factory (`app/__init__.py`) with clean separation between thin blueprints
(`app/blueprints/*`) and a deep service layer (`app/services/*`), where the genuinely complex
domains (training generation, plan mutation, workout state, pump-check comparison, wearables)
each live in a cohesive package with `models`/`queries`/`service` submodules. Non-obvious
decisions carry rationale comments referencing the incident or invariant that motivated them,
and — more importantly — those invariants are enforced in code (boot-time `RuntimeError`s) and
pinned by regression tests rather than left as prose.

**Dominant constraint / main tech-debt hotspot:** the process-local single-worker assumption.
AI concurrency semaphores, the in-memory limiter fallback, the capacity gauges, and leaderboard
hydration all assume `FITX_WEB_WORKERS=1` (enforced at `ai_gate.py:283-287`). Correct for the
1-worker/8-thread EC2 topology, but a hard scaling ceiling: any move to multiple workers or
horizontal scale-out requires re-homing AI gating and rate-limiting into a shared store/queue.

**Secondary hotspot:** `app/db_init.py` conflates schema creation, Alembic reconciliation, and
data seeding into one function with interleaved commits (see F2) — the least-clean module in an
otherwise disciplined codebase.

## Coverage — verified good (checked, not issues)

- **JWT:** algorithm pinned to `RS256` (blocks `alg=none`/HS256 confusion), issuer/audience/`token_use`
  checked, request auth requires an **access** token not ID token, leeway pinned to 0.
- **CSRF:** two-layer (Origin/Referer + per-session synchronizer via `secrets.compare_digest`);
  mobile API correctly exempt (Bearer-only); logout has its own default-deny guard.
- **SSRF** (`menu_fetch.py`): positive `is_global` IP allowlist, IPv4-mapped-IPv6 unwrap, port
  allowlist, per-hop re-validation, DNS-rebinding TOCTOU closed via pinned `getaddrinfo`.
- **IDOR / ownership:** consistently scoped to `current_user.id`; S3 helper enforces
  `_key_belongs_to`; coach context has an `assert_principal` cross-user guard.
- **SQL injection:** all ORM; the only `text()` uses are constant index predicates.
- **AI prompt injection:** friend content fenced as data with invisible-char/fence-token
  stripping; plan-mutation tools capability-gated, `user_id` never from the model, fail-closed.
- **File upload:** content-verified (not MIME-trusted), decompression-bomb guarded, pixel/byte caps.
- **XSS output:** `textContent`-based escaping throughout; coach markdown via
  `DOMPurify.sanitize(marked.parse(...))`. No `eval`/`document.write`/unsanitized `innerHTML`.
- **Secrets/PII:** no hardcoded keys; S3 via IAM instance profile; provider tokens Fernet-encrypted
  and `repr=False`; error/barcode logging omits values.
- **Migrations:** single Alembic head (`c2d3e4f5a6b7`); expand/contract respected (drops only in
  `downgrade()`); table-creating migrations after the stamp are idempotent via `has_table` guards.
- **Auth fail-closed:** `LOGIN_FAIL_CLOSED` on by default; JWKS-unavailable → 503, never 401.
- **DB-pool vs thread invariant:** `gunicorn.conf.py` and `ai_gate`/`config.py` read the same
  `FITX_WEB_THREADS`; `enforce_gate_invariants` raises in non-dev when reserve < 2 or
  `pool+overflow < threads`.
- **Feature flags** never read from the request; resolved through a strict parser into
  `current_app.config`.
- **Streaming B-rule / gate release / partial-response persistence:** fallback gated on
  `not parts and tools_ran == 0`; slots released exactly once via `Event`-guarded `_release`;
  interrupted partial recorded exactly once.
- **Workout completion/session:** fixed lock order, `uq_pump_check_day` durable claim,
  race-loser reconciliation, fail-closed IntegrityError classification.
- **Training history/progression:** trailing weekly windows contiguous/non-overlapping and never
  past `end_day`; Epley 1RM correct; no division-by-zero (guards on `< 2` active values).
- **Plan mutation:** `(user_id, idempotency_key)` uniqueness, byte-snapshot undo precondition,
  per-turn budget with duplicate-key no-charge.
- **Challenges/gamification day-dedup:** `water_logged` over-count fixed via `WaterLog.quest_fired`
  conditional UPDATE gated by `uq_user_water_day`.
- **Timezone/date:** no raw `date.today()`/`utcnow().date()` in day-boundary logic — everything
  routes through `app/timeutil`.
