Automated deep-dive triage of the FitX codebase by three parallel agents:
**(1) security & auth**, **(2) correctness / data-integrity**, and
**(3) AI-pipeline / infra / ops**. Verified against the current code on branch
`claude/amazing-dijkstra-oslt8f` (HEAD `22a5f35`, "tx-safe challenges + orphan
notification cleanup", #164).

Every finding below was re-checked against source by hand before inclusion. One
agent-reported **High** (fresh-DB boot migration failure) was **investigated and

the negative result is on record and nobody re-opens it.

## Headline

The codebase remains **very well-hardened**. There is **no Critical or High**
security *or* correctness issue in this pass. Auth/JWT/CSRF/CSP/SSRF/IDOR
controls are sound (not nominal), the challenge/leaderboard funnels use
`with_for_update` + savepoint poison-protection correctly, cascade deletes and
keyset pagination are correct, and every canonical `MealLog` write goes through
idempotency + macro-clamp — with **two exceptions** noted below.

The only items with real user-facing impact are two **Medium** correctness bugs:
a gamification challenge that completes on the wrong condition, and a
suggestion-accept path that can double-write a meal under a concurrent submit.
Everything else is Low / defense-in-depth / accepted tradeoff.

## Medium

### 1. `weekly_water` challenge counts events, not distinct days
**Files:** `app/services/challenges.py:184-186` (seed) · `app/blueprints/training.py:347` (`set_water`) · `app/services/gamification.py:281-282` (`_claim_quest`) · `app/services/challenges.py:64` (`record_event`)

The challenge is seeded as *"Bu hafta 5 gün su takibini gir"* (`metric="water_logged"`, `target_value=5`) — i.e. **5 distinct days**. But it is driven by an event funnel that fires on **every** water POST:

- `set_water` calls `complete_quest_for_user(user_id, "water_logged")` on every request with `count > 0` (`training.py:346-347`).
- `_claim_quest` calls `record_event(user_id, "water_logged")` **unconditionally, at the top**, *before* the once-per-day quest dedup (`gamification.py:281-282`).
- `record_event` has **no per-day dedup** — it does `progress = progress + amount` on every call (verified at `challenges.py`, the `begin_nested` UPDATE block).

The daily *quest* is correctly day-deduped (`uq_user_quest_day`); only the **challenge** over-counts. Contrast `active_day`, which is correct because its caller (`update_streak`, `hooks.py:311`) fires it only on the day's first activity — the dedup lives at the caller, not in `record_event`.

**Failure scenario:** a user sets their water glass-by-glass (1→2→3→4→5 = 5 POSTs) in one afternoon → `weekly_water` progress hits 5 and the challenge completes (75 XP + feed activity) on a **single day**, instead of requiring 5 separate days.

**Fix direction:** gate `water_logged` challenge progress to the day's first water log — mirror the `active_day` pattern (only fire `record_event("water_logged")` when the `WaterLog` row for today is first created / first crosses 0), rather than on every `set_water` POST.

### 2. Suggestion-accept can duplicate a `MealLog` under concurrent submit
**Files:** `app/blueprints/social.py:871-917` (`respond_suggestion`) + `_process_meal_suggestion_accept:920-1015`

Every other canonical `MealLog`-writing path (`log_meal`, `quick_add_meal`, `diary_log_meal`, barcode add) uses `meal_idempotency.commit_once` or a guarded conditional `UPDATE`. This path uses a plain check-then-act on `msg.message_type` with **no** conditional UPDATE and **no** idempotency key:

```python
is_meal = msg.message_type == "suggestion_meal"   # both concurrent requests read this
...
msg.message_type = msg.message_type + "_accepted" # non-atomic mutate
if is_meal:
    nutrients = _process_meal_suggestion_accept(msg)  # db.session.add(MealLog)
db.session.commit()
```

Sequential replays are safe (the `_accepted` state guard), but there is no protection against **concurrency**, unlike the sibling `friend_accept` path (`social.py:653`) which uses a guarded `UPDATE ... WHERE`.

**Failure scenario:** two concurrent `POST /suggest/respond/<msg_id>` with `action=accept` (double-tap / client retry). Both read `message_type == "suggestion_meal"`, both pass the guard, both add a reply `Message` and a `MealLog`, both commit → **two MealLog rows** (inflated daily calories/macros, skewed protein nudge + weekly report) plus a duplicate confirmation message.

**Fix direction:** serialize with a guarded `UPDATE ... WHERE message_type = 'suggestion_meal'` (mirror `friend_accept` at line 653) so only one request transitions the state and writes the meal; optionally route the write through `meal_idempotency`.

### 3. `_heavy_chat` holds the model-concurrency slot across both providers, all retries, and backoff sleeps
**File:** `app/services/ai.py:163` (`with model_concurrency_slot():` spanning L163-189)

The single `model_concurrency_slot()` (default `AI_MODEL_MAX_CONCURRENCY=4`) wraps the **entire** routine: the Bedrock `call_with_recovery` (jittered retries with `time.sleep`), the OpenAI fallback (its own retries + sleeps), and the last-good recall. A slot is thus held for the full multi-second-to-minute duration during a provider incident, not just the active network call. Contrast the coach loops (`ai_coach.py:1097`, `1010`), which correctly scope the slot to a single `create()` call.

**Failure scenario:** during a Bedrock outage, 4 concurrent `_heavy_chat` callers (nutrition search / menu extraction) each pin a model slot through Bedrock retries → OpenAI retries → sleeps; other model callers block behind them, serializing unrelated AI work exactly when the system is already degraded. Bounded by the failure-cooldown, but amplifies latency during incidents.

**Fix direction:** scope `model_concurrency_slot()` to each individual provider `create()` call (release it around retry sleeps and across the Bedrock→OpenAI switch), as the coach loops already do.

### 4. Inline summarization runs a blocking LLM call on the `/ask` critical path when no worker is present
**Files:** `app/services/ai_pipeline.py:24` (`_maybe_enqueue_summarize`) → `app/jobs/__init__.py:80` (`enqueue_or_run` inline branch) → `app/services/memory_manager.py:287`

`_memory_stage` enqueues `summarize_conversation` every turn. The RQ worker is documented as **optional** and is frequently not running; `enqueue_or_run` then executes the job **inline**. When the unsummarized backlog exceeds `AI_SUMMARY_TRIGGER_TOKENS`, `maybe_summarize` makes a blocking `gpt-4o-mini` call **before** the main coach turn — inside the `ai_concurrency_gate` slot and **not** wrapped in `model_concurrency_slot` or `call_with_recovery`.

**Failure scenario:** a long-running conversation on a worker-less deployment pays a second synchronous OpenAI round-trip on the critical `/ask` path (~doubled perceived latency on the heaviest turns) and holds the AI gate slot longer.

**Fix direction:** in the inline fallback, run summarization **after** the response is produced (defer it), and/or gate + recovery-wrap the summarize LLM call so it can't starve the coach path.

## Low

### 5. `pump_check_gallery_delete` orphans like/comment children on SQLite
**File:** `app/blueprints/profile.py:208-228`

The delete explicitly cleans up FK-less `FeedItem` refs + notifications and `db.session.delete(check)`, but relies on DB `ON DELETE CASCADE` for `PumpCheckLike`/`PumpCheckComment` (collections aren't loaded → no ORM cascade). On Postgres (prod) this is fine; on SQLite (local/tests, `PRAGMA foreign_keys` off — which `_purge_user` in `cli.py` explicitly compensates for) these child rows are orphaned. Dev/test-only, but inconsistent with the deliberate SQLite-safe pattern used elsewhere.

**Fix direction:** delete `PumpCheckLike`/`PumpCheckComment` for the `check_id` explicitly before `db.session.delete(check)`, matching `_purge_user`.

### 6. Streaming producer thread keeps generating after client disconnect
**File:** `app/services/ai_stream.py:67-88` (`_stream_bedrock_turn` daemon thread)

Each streamed turn spawns a daemon thread that acquires `model_concurrency_slot()` and drives `messages_client.stream(...)`. On client disconnect (`GeneratorExit` through `ai_pipeline.stream_answer`), the consumer generator exits but the producer thread runs until the Bedrock stream naturally completes — still consuming (billed) tokens and holding the model slot for a user who is gone.

**Fix direction:** signal cancellation to the producer thread on `GeneratorExit` (a stop flag checked in the `text_stream` loop) so it exits and releases the slot promptly.

### 7. Redis password on the process command line
**File:** `docker-compose.yml:78-84` (`redis-server ... --requirepass "$$REDIS_PASSWORD"`)

The password is interpolated into `redis-server` argv → visible via `ps` / `/proc/<pid>/cmdline` inside the container and in `docker inspect`. Loopback-only binding limits blast radius, but the secret is more exposed than the env-var approach used elsewhere.

**Fix direction:** pass `requirepass` via a mounted `redis.conf` (or the already-present `REDIS_PASSWORD` env) instead of the command line.

### 8. `friend_reject` leaves a stale unread `friend_request` notification
**File:** `app/blueprints/social.py:669-680`

`friend_request_cancel` purges the receiver's unread `friend_request` notification; `friend_reject` does not. Since the rejecter *is* the recipient, the stale unread row is cosmetic, but it's an asymmetry.

**Fix direction:** purge the corresponding unread `friend_request` notification in `friend_reject`, mirroring `friend_request_cancel`.

### 9. CSP: wildcard GTM script host + retained inline-style-attr (documented tradeoffs)
**File:** `app/hooks.py:54` (`script-src` includes `https://*.googletagmanager.com`), `:65,67` (`style-src`/`style-src-attr 'unsafe-inline'`)

Both are defense-in-depth weakenings, **not currently reachable** — the audit found no HTML-injection sink (all user content is `esc()`/`textContent`-escaped, usernames charset-restricted). `style-src-elem` is correctly nonce-locked. Flagged only so the residual is a conscious choice.

**Fix direction (optional):** pin the exact gtag host(s) instead of the wildcard; move progress-bar widths to nonce'd `<style>`/CSS custom properties and drop `style-src-attr 'unsafe-inline'`.

### 10. Per-username login limiter enables a short self-healing lockout DoS (documented tradeoff)
**File:** `app/blueprints/auth.py:382-383` (`_login_username_key`, docstring `:109-119`)

A second login limit keyed on the submitted username (15 failed / 15 min) lets an attacker who knows a victim's username burn that budget → victim gets 429 for ≤15 min. Usernames are discoverable via friend search. The alternative (no per-account throttle) is worse. Acceptable as-is; a CAPTCHA step instead of a hard 429 would remove the DoS.

## Info / accepted residual

### 11. Cross-turn residual on the stage→confirm injection guard
**File:** `app/services/ai_coach.py:178-197`, `267-286`

The deterministic same-turn lock (`_staged_this_turn`) blocks the classic "inject → stage → confirm in one turn" auto-commit. It resets each turn, so a `PendingAction` staged via friend-content injection in turn N *could* be committed in turn N+1 if an injection re-triggers `confirm_and_commit_meal_log` before the 1-hour stale-pending TTL. Blast radius is intentionally tiny (logs a meal/workout to the user's **own** account; `user_id` never comes from the LLM; macros are clamped), so this is an accepted residual, not a live vulnerability. Optional hardening: require that a committed `PendingAction` was actually surfaced to the user (a "presented" marker) before allowing commit.

## Investigated & dismissed (false positive)

### ✗ "Fresh-DB boot fails: `ab12cd34ef56` / `e7f8a9b0c1d2` lack the `has_table` guard" — NOT A BUG
One agent flagged `migrations/versions/ab12cd34ef56_add_wearable_integrations.py` and `e7f8a9b0c1d2_add_barcode_food_cache.py` as unconditional `op.create_table` that would collide with `db.create_all()` on a fresh boot.

**Why it's wrong:** the fresh-boot path (`app/db_init.py:139-146`) does `create_all()` → `stamp("aa11bb22cc33")` → `upgrade()`. Both flagged migrations are **ancestors** of the stamp point `aa11bb22cc33` (chain: `…→ab12cd34ef56→…→d6e7f8a9b0c1` and `…→e7f8a9b0c1d2` both feed the merge `f8a9b0c1d2e3`, whose descendant is `aa11bb22cc33`). Alembic therefore treats them as **already-applied** when the DB is stamped, and **never re-runs them** on fresh boot. Verified directly: the only migrations that run *post-stamp* and create tables — `cc33dd44ee55`, `dd44ee55ff66`, `ee55ff66aa77`, `ff66aa77bb88` — **all carry the `has_table` guard**. The fresh-boot contract is intact.

## Areas audited and confirmed clean

- **JWT** (`cognito_jwt.py`): RS256 pinned (no `alg:none`/confusion), iss/aud/`token_use`/`exp` all enforced vs live JWKS; transient-vs-invalid distinguished so outages don't mass-logout.
- **IDOR / ownership**: every by-ID route checked scopes to `current_user.id` or gates via `can_view_pump_check` (diary, social like/comment/delete/repost, profile, supplements, wearables); repost refuses to widen audience.
- **Session/token store** (`session_store.py`): Fernet-encrypted tokens, `expected_user_id` + absolute/idle timeouts, sub→user rebind per request.
- **CSRF** (`hooks.py`): two-layer (Origin/Referer + per-session synchronizer, `compare_digest`); GET logout has its own Sec-Fetch guard; wearable OAuth `state` validated.
- **SSRF** (`menu_fetch.py`): positive `is_global` IP allowlist, port 80/443 only, per-hop re-validation + DNS-pinning against rebinding.
- **Uploads** (`s3_helper.py`, `avatars.py`, `validators.py`): data-URL regex gate, strict base64, Pillow `verify()` + pixel-bomb guard (fails closed in prod), UUID S3 keys, `_key_belongs_to` gate, IAM instance-profile creds.
- **Timezone / day-keys**: blueprints consistently use `app_today()`/`day_key()`/`utc_day_bounds()`; remaining `utcnow()` uses are relative-window/naive-UTC `created_at`, not day-boundary logic.
- **Leaderboard / weekly rollover**: Istanbul Sunday-23:59 boundary consistent, idempotent (`WeeklyResetLog` UNIQUE), Redis after-commit/after-rollback dirty-flush, no `_lb_score` collision.
- **XP concurrency**: `award_xp` / counters / `update_streak` / `supplement_add` use `with_for_update()` on a column query (C1 fix) → no lost update.
- **Challenge funnel** (`challenges.py`): savepoint-per-challenge poison protection, `no_autoflush` catalog reads, guarded one-time completion (`WHERE completed_at IS NULL`), `count_challenge_xp=False` recursion breaker.
- **Feed V2 keyset pagination** (`feed.py`): cross-source `(created_at, source_rank, id)` keyset correct in all branches; no gaps/dupes.
- **Meal idempotency + macro-clamp**: applied on every canonical MealLog path **except** the suggestion-accept path in Finding #2.
- **AI provider B-rule** (`ai_stream`, `ai_coach`): Bedrock→OpenAI fallback only when no delta emitted **and** no tool side-effect. Correct across all error branches.
- **SSE leakage**: error frames carry only i18n keys; raw provider text stays server-side.
- **Cache keys** (`ai_cache`, `foodcache`, `ai_recovery.lastgood_key`): user-agnostic caches are legitimately so; last-good keyed on full `sha256(model+system+messages+max_tokens)` → no cross-user bleed.
- **Concurrency-gate math**: `AI_MAX_CONCURRENCY(4) + SCRAPE(2) = 6 ≤ FITX_WEB_THREADS(8) − 2`; model-slot adds no extra gunicorn-thread pressure.
- **Worker DB safety**: both `worker.py` and `jobs/tasks.py` set `FITX_SKIP_DB_INIT=1` before `create_app`; per-job `db.session.remove()`.
- **Prompt-injection fencing** (`context_builder.neutralize_friend_content`): strips `FRIEND_DATA` fence tokens + zero-width/bidi control chars before fencing third-party content.
