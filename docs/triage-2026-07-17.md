## Headline

The codebase is **exceptionally well-hardened**. No Critical/High **security**
vulnerability exists — auth/JWT/CSRF/CSP/SSRF/IDOR controls are genuinely sound
(not nominal), migrations are re-entrant, cascade deletes are complete, and
concurrency-sensitive counters use `with_for_update`. The one item that can hurt
real users in normal operation is a **transaction-poisoning bug** in the new
Challenges funnel that surfaces as intermittent 500s; the one item that can lose
**data** is the missing backstop on destructive-migration rollback.

## High

### 1. Destructive-migration rollback has no reliable safety net
**File:** `.github/workflows/deploy.yml:39-59, 66-81, 94`

The health-gate rollback does `git reset --hard $PREV_COMMIT && docker compose up
-d --build` — it reverts **code only**, never the DB (documented as A2 in
CLAUDE.md: boot auto-applies migrations, rollback does not undo them). The sole
mitigation — a pre-deploy RDS snapshot — is `continue-on-error: true` **and**
silently skips entirely when `vars.RDS_INSTANCE_ID` is unset
(`echo "...ATLANDI"; exit 0`).

**Failure scenario:** a forward-applied destructive migration (column/table
drop or rename) + rolled-back code = unrecoverable state, with **zero backup**
if `RDS_INSTANCE_ID` isn't configured — and the pipeline still reports the
snapshot step green. This is the single scenario that can lose real user data
irrecoverably.

**Fix:** make the snapshot step **blocking** (fail the deploy if
`RDS_INSTANCE_ID` is missing or `rds:CreateDBSnapshot` is denied); or, for known
destructive migrations, follow the CLAUDE.md escape hatch — set
`FITX_DB_AUTO_UPGRADE=0` and run the migration as a separate, explicitly-approved
one-shot step. Continue writing migrations expand/contract so code rollback stays
safe.

## Medium

### 2. `record_event` swallows DB errors without rollback → poisons the caller's transaction → `update_streak` 500s
**Files:** `app/services/challenges.py:93-96` (mirror in
`app/services/gamification.py:105-110`), triggered by `app/hooks.py:296` +
unguarded commit at `app/hooks.py:305`

`record_event` wraps its whole body in `except Exception: log.warning(...)` and
**never calls `db.session.rollback()`**. The get-or-create is savepoint-protected
(`begin_nested`), but the subsequent `UPDATE progress+amount`,
`db.session.refresh(row)`, and the completion path (`_try_complete` → `award_xp`
/ `award_badge` / `notify` / `log_activity`) all run in the **caller's outer
transaction**. A transient DB error there (deadlock, lock timeout, connection
blip — realistic with 8 threads all taking `FOR UPDATE` locks on User/challenge
rows) aborts the Postgres transaction and marks the SQLAlchemy session for
rollback. `record_event` swallows the Python exception and returns normally,
leaving the session **poisoned**.

`update_streak` runs as a `before_request` on every authenticated request and
commits with **no try/except**:

```python
record_event(user.id, "active_day")   # hooks.py:296 — may poison session, error swallowed
...
db.session.commit()                    # hooks.py:305 — raises PendingRollbackError → 500
```

**Failure scenario:** two requests deadlock on challenge/User row locks during
the daily first-request streak update → the loser's `record_event` swallows the
error → the bare `commit()` raises `PendingRollbackError` → the page request
returns **500**. Flask teardown rolls back so it's per-request (not a permanent
outage), but under contention users see intermittent 500s on normal navigation.
The broad catch is meant to guarantee "challenge progress never breaks the main
action," but without a rollback it fails to deliver that for any caller that
commits.

**Fix:** in `record_event`'s (and `award_xp`'s inner `record_event`) except
block, call `db.session.rollback()` — or wrap the per-challenge work in
`db.session.begin_nested()` so a failure only rolls back the savepoint and leaves
the outer transaction usable. Additionally, guard `update_streak`'s commit with
try/except + rollback (every other write path already does this).

### 3. Three deploy verification steps are advisory-only (non-blocking)
**File:** `.github/workflows/deploy.yml:39-59, 66`

The Cognito pool-drift check, the CustomEmailSender Lambda package check, and the
RDS snapshot are all `continue-on-error: true`. The Lambda check has **already
caused a silent production incident** (see the inline comment at lines 48-52:
vendored deps missing → auth emails silently never sent → nobody could register).
They remain non-blocking pending IAM permissions.

**Why it matters:** these guard exactly the "green deploy, broken prod" class the
pipeline exists to catch, but currently only log.

**Fix:** grant the two IAM permissions (`cognito-idp:DescribeUserPool*`,
`lambda:GetFunction`) and drop `continue-on-error` per the TODOs already in the
file.

### 4. `ai_coach.py` remains a 1181-line god-module + wide re-export shim
**File:** `app/services/ai_coach.py:25-53`

Sprint 4 extracted the pipeline into `ai_pipeline`/`context_builder`/
`memory_manager`/`prompt_builder`/`response_formatter`, but `ai_coach` still holds
all tool implementations *and* the provider loops, *and* re-exports old names from
5 modules (4 `# noqa: F401` blocks). Five app modules (`ai_pipeline`, `ai_stream`,
`coach`, `food`, `tracking`) plus tests import through this shim, so the "real"
definition of a symbol may live in one of five other files — high cognitive load,
easy to introduce import cycles.

**Fix:** deliberate compat surface — schedule the follow-through rather than treat
as urgent. Collapse the re-exports once the monkeypatch/test surface is migrated
to the new module paths.

### 5. High density of silent exception swallowing
**Files:** `app/` broadly (104 `except Exception`/bare `except`; 8 `except: pass`
in `app/services/`); notably `app/db_init.py:114-125`

Most of this is intentional fail-soft design (Redis/Sentry/metrics/cache no-op),
which is correct. But the truly-silent `except: pass` cases (no log, no
request_id) can hide genuine regressions — e.g. `db_init.py` swallows both
`seed_challenges()` and `backfill_referral_codes()` failures with only a
`rollback()`, no log line. A broken seed/backfill then disappears with no signal.

**Fix:** ensure every swallow logs at least `warning` with
`current_request_id()`; reserve truly-silent `pass` for the metrics/telemetry
paths only.

## Low

### 6. Coach "confirm workout" tool omits the `workout_logged` quest/challenge funnel
**File:** `app/services/ai_coach.py:395-432` (`_tool_confirm_and_commit_workout_log`)

Writes a `WorkoutLog` + `award_xp(user_id, 15)` but does **not** call
`_claim_quest("workout_logged")` / `record_event("workout_logged")`. Both other
WorkoutLog writers do (`/workout/complete` at `training.py:229`; the pump-check AI
tool at `ai_coach.py:721`). So a workout logged through coach conversation never
counts toward the daily `workout_logged` quest or the `weekly_workouts`/`grinder`
challenges (it still feeds `xp_earned`). Possibly intentional (the coach logs
individual exercises; per-exercise firing would over-count session-based
challenges) — needs a product decision. If intended, add a code comment so it
doesn't read as a bug.

### 7. Global challenge leaderboard exposes strangers' `full_name`
**Files:** `app/services/challenges.py:187` (`_board_entry`), via
`app/blueprints/challenges.py:68` (`challenge_leaderboard`, `scope=global`)

Any authenticated user gets the top-50 participants' real `full_name`, `user_id`,
and avatar for a global challenge, regardless of friendship. Consistent with the
app's existing exposure model (`friends_search`/`friends_select_list` already
return `full_name` to any searcher), so not a new leak. Optional hardening: return
`username` only for non-friends in global scope.

### 8. Boot-time migrations run inside the serving process — safe only at `workers=1`
**Files:** `app/db_init.py:16-64`, `gunicorn.conf.py:13`

`init_database()` runs `upgrade()` + `create_all()` synchronously inside
`create_app()` (the gunicorn worker). Safe today (`workers=1`), but a latent
landmine: raising `FITX_WEB_WORKERS` or any multi-container scale-out races
concurrent boot upgrades against one RDS. The same single-worker assumption also
underpins the in-process `ai_gate` semaphores and in-memory limiter fallback.

**Fix:** none needed now; add a boot assertion/warn if `workers>1` while
`FITX_DB_AUTO_UPGRADE!=0`.

### 9. `ai_gate` thread-reserve defaults sit exactly at the minimum
**File:** `app/services/ai_gate.py:32-83`

`AI_MAX_CONCURRENCY=4` + `SCRAPE_MAX_CONCURRENCY=2` = 6 against
`FITX_WEB_THREADS=8` → reserve = 2 = `THREAD_RESERVE_MIN`. Passes with zero
headroom; any env bump only logs a `warning` (`warn_if_gates_exhaust_threads`) and
boots anyway. (`_model_slots`, default 4, is correctly excluded from the reserve
math because it's acquired nested inside an AI route slot — worth a comment.)

**Fix:** consider failing boot on a reserve violation (or lower the AI default to
3) so the guard is enforced, not merely logged.

### 10. Deep-health probe does outbound work on every gate poll
**File:** `app/__init__.py:110-122`

`/health?deep=1` fires a live 3s HTTP request to the FatSecret proxy (plus
`worker_alive()`/Redis) on every call; the deploy gate polls it up to 30×
(`deploy.yml:94`). Couples the gate's latency to an external service (the
FatSecret field is informational and can't fail the gate — latency only, not a
false rollback).

**Fix:** cache the FatSecret probe briefly or move it behind a separate
`?probe=fatsecret` flag.

### 11. `feed_report` / `feed_hide` accept arbitrary target IDs
**File:** `app/blueprints/social.py:501-551`

`_parse_mod_target` validates only `target_type ∈ {pump_check, feed_item,
activity}` and that `target_id` is an int — not that the target is visible to the
caller. A user can create `FeedReport`/`FeedHide` rows referencing content they
can't see. Existence is not revealed (generic `{ok: true}`), impact is limited to
self-scoped rows, both are dedup-guarded, and `feed_report` is rate-limited. No
action strictly required.

## Verified sound (no action needed)

- **Authorization / IDOR:** every by-ID load verifies ownership across social /
  profile / nutrition / food / tracking / training / gamification / supplements /
  challenges / notifications; pump-check/feed visibility enforced via
  `can_view_pump_check` / `_visible_*_or_403`; stale-authorization handled
  (friendship removal drops access).
- **Auth / Cognito:** full RS256/JWKS signature check, essential `exp`, issuer,
  `token_use`, audience validation; `require_auth` re-validates every request and
  rebinds the verified `sub`; transient JWKS failure → 503 without destroying the
  session; login has per-IP/per-username limits, fail-closed on Redis-down,
  session-fixation clearing, enumeration hardening.
- **CSRF / CSP:** global `before_request` Origin/Referer + per-session
  synchronizer token (constant-time); per-request nonce, no `unsafe-inline`,
  pinned jsdelivr, `object-src/frame-ancestors/base-uri` locked down.
- **SSRF (menu scraper):** positive IP allowlist, IPv4-mapped-IPv6 unwrap, port
  allowlist, per-hop re-validation, DNS-pinning (closes rebinding TOCTOU), body
  size cap.
- **Injection / path traversal:** parameterized SQL throughout; S3 keys built
  server-side from UUID + `user_id` with segment-equality ownership checks.
- **Secrets:** none hardcoded; only `.env.example` placeholders are tracked.
- **Migration re-runnability:** every migration after the `aa11bb22cc33` stamp
  point carries `has_table()`/`has_column()` guards; fresh-DB boot invariant holds
  and is exercised by `tests/test_db_init.py`.
- **Correctness core:** `award_xp`/`update_streak` use C1 column-lock reads;
  challenge progress uses atomic `progress + amount` UPDATEs + `WHERE completed_at
  IS NULL` guarded one-time completion; B16 (fallback not persisted) holds in both
  blocking and streaming paths; provider fallback correctly gated on `not parts
  and tools_ran == 0`; Istanbul day-keys consistent (no direct
  `date.today()`/`strftime` day-key violations); every MealLog write routes
  through `clamp_serving_macros`.
- **Config / cascade / cookies:** prod fail-fast on missing secrets, TLS
  enforcement, Secure/HttpOnly/SameSite cookies, `LOGIN_FAIL_CLOSED=1` default;
  all 24 `user_id`-bearing models covered in `cli._user_child_models`; deps fully
  `==`-pinned + base image `@sha256`-pinned + Dependabot.
