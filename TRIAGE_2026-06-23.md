**Bottom line:** The codebase is well-hardened. **No new exploitable Critical/High
*security* vulnerabilities.** However there are several genuine **new bugs**, the most
important being a **HIGH data-integrity** issue: a second meal-logging path that still
writes zero-macro rows into the canonical `MealLog` ledger — the exact bug class that
was already fixed in `meallog.py` but missed in this sibling path.

## 🔴 HIGH

### 1. Social suggestion-accept writes 0-macro rows into the canonical MealLog ledger ✅ verified
- **File:** `app/blueprints/social.py:327-335` and `:376-398` (`_process_meal_suggestion_accept`)
- **Problem:** When a user accepts a friend's meal suggestion, two failure paths still
  `db.session.add()` a `MealLog` with `kalori=0, protein=0, karb=0, yag=0`:
  (a) the body can't be parsed into items (`:327` → unconditional zero row at `:329-335`);
  (b) the macro pipeline's outer `except` swallows the error and the inner LLM fallback
  also fails (`:386 pass`), leaving `total` all-zero, which is then committed at `:389-398`.
  The user sees a generic success. This is the **same canonical-ledger corruption that
  `TRIAGE_FIXES #1` fixed in `meallog.py`** (via a `parsed_ok` guard → HTTP 502) — but this
  sibling write path was never patched. Permanent zero-macro rows silently corrupt daily
  totals, the protein nudge, the menu `consumed`/`remaining` math, and weekly reports.
- **Fix:** Mirror the `meallog.py` fix — if items don't parse or macros come back all-zero,
  do **not** add the `MealLog` row; surface an error (or skip the write) instead of writing zeros.
  At minimum gate `db.session.add(entry)` on a non-zero total.

### 2. `friend_accept` double-XP race (check-then-act, no lock) ✅ verified
- **File:** `app/blueprints/social.py:155-162`
- **Problem:** Two concurrent `POST /friend/accept/<id>` both read `fr.status == "pending"`,
  both run `award_xp(...,50)` ×2 + `log_activity` ×2 before either commits → duplicate +50 XP
  to both users and duplicate feed rows. `status` is in no unique constraint and there's no
  `with_for_update()`. The codebase already uses the correct pattern elsewhere
  (`tracking.py` IntegrityError-guarded, `hooks.py:173` `with_for_update`), so this is an
  inconsistency, not a missing capability.
- **Fix:** Guarded conditional update — `UPDATE friendship SET status='accepted' WHERE id=:id
  AND status='pending'`; award only when `rowcount == 1`.

### 3. Referral claim race + multi-commit partial state ✅ verified
- **File:** `app/services/referral.py:51-65`, callers in `app/blueprints/auth.py` register paths
- **Problem:** `consume_referral` does a read-modify-write on `new_user.referred_by_id` with no
  lock/unique guard, then `award_xp` ×2. Two concurrent claims (body `ref` + cookie `fitx_ref`,
  or a retried POST) can both pass the guard → double `REFERRAL_REWARD_XP` (75 each). Separately,
  the inviter/invitee link+XP commit and the `complete_quest_for_user` commit are **two
  transactions**, and in register the user is committed before `consume_referral` runs in yet
  another transaction — a crash between them silently loses the referral.
- **Fix:** Conditional `UPDATE ... WHERE referred_by_id IS NULL`, award only on `rowcount == 1`;
  fold the writes into one transaction the caller commits.

## 🟠 MEDIUM

### 4. State-changing mutation behind a GET — `chat_messages` (CSRF-unguarded) ✅ verified
- **File:** `app/blueprints/social.py:200-209`
- **Problem:** `GET /chat/<username>/messages` runs `Message...update({"is_read": True})` +
  `commit()`. Per CLAUDE.md the CSRF guard only fires on write methods, so this side effect is
  **not CSRF-protected** and is triggerable by prefetch / cross-origin navigation to silently
  mark a victim's messages read. Violates the project rule "state-changing route'u GET olarak açma."
- **Fix:** Move the read-receipt write to a POST endpoint (or accept as benign and document it).

### 5. AI-coach staged macros bypass portion-sanity validation into the ledger ✅ verified
- **File:** `app/services/ai_coach.py:425-446` (`_tool_confirm_and_commit_meal_log`)
- **Problem:** Macros are taken straight from `pending.payload` via `float(...)` and written to
  `MealLog` with no `nutrition_pipeline.check_serving` / clamp — unlike the UI/diary/menu paths
  which all sanitize. A bad FatSecret/LLM value lands unvalidated in the canonical ledger. The
  DB `CHECK` only catches gross overflow (≤100000 kcal), not "3000 kcal" garbage.
- **Fix:** Route staged macros through the same `nutrition_pipeline` clamp before insert.

### 6. Unhandled `ValueError` (HTTP 500) on non-numeric `steps` ✅ verified
- **File:** `app/blueprints/tracking.py:259` — `steps = int(data.get("steps", 0))`
- **Problem:** `"steps": "abc"`/`""` throws `ValueError` before the validation guards → unhandled
  HTTP 500. Identical bug class to the `checkin` route fix (`TRIAGE_FIXES #3`, now `_to_int`),
  but this route was missed. `_to_int` is already imported (`tracking.py:12`).
  *(Flagged independently by both the security and logic agents.)*
- **Fix:** `steps = _to_int(data.get("steps", 0), 0)` — the `steps <= 0` guard then handles bad values.

### 7. `register` Cognito sign-up precedes local commit → orphaned Cognito account ✅ verified
- **File:** `app/blueprints/auth.py:105-117`
- **Problem:** Remote `cognito_idp.sign_up` happens before `db.session.commit()`. If the local
  commit throws, the Cognito user exists with no local row; retry hits "username exists" and the
  user is wedged. No compensating action.
- **Fix:** On local-commit failure, best-effort delete/disable the Cognito user, or make creation
  idempotent against a pre-existing `cognito_sub` on retry.

### 8. Double-submit on diary meal create → IntegrityError 500 ✅ verified
- **File:** `app/blueprints/nutrition/diary.py:115-135` (`diary_create_meal`)
- **Problem:** Check-then-insert against `uq_custom_meal_day` with no IntegrityError handling.
  Two concurrent POSTs both pass the `existing` check, both INSERT, second violates the
  constraint → HTTP 500. Sibling routes (`set_water`, `log_daily_activity`) already catch and
  re-fetch — this one is the odd one out.
- **Fix:** Wrap commit in `try/except IntegrityError`, rollback, re-query and return the existing row.

### 9. PII / user content written to application logs ✅ verified
- **File:** `app/blueprints/social.py:328, 349, 377, 399` (and related)
- **Problem:** `logger.warning(f"... from: {msg.body[:100]}")` logs user-authored message/meal
  content and other users' names into app logs.
- **Fix:** Log only metadata (message id, length, item count); drop body/name substrings.

## 🟡 LOW / informational

10. **`s3_helper.py:131,153`** ownership check is a substring match (`f"/{uid}/" not in key`)
    rather than parsing the user_id path segment. Not exploitable today (keys are server-generated)
    but fragile defense-in-depth. Parse and compare equality.
11. **`app/services/ai_coach.py` `cancel_pending_log`** deletes ALL pending actions for the user,
    unscoped by `action_type` — one "iptal" wipes both a staged meal and a staged workout.
12. **`app/services/foodcache.py:54`** caches macro dicts by reference (no defensive copy) and
    reads outside `_cache_lock`. Latent; add `cache[name] = dict(macros)` and lock the read.
    Also inconsistent key normalization (`_cache_macros` raw vs `_cache_food_id` lowercased).
13. **`app/services/fatsecret.py:272-294`** 150g serving-weight fallback still scales
    per-serving→per-100g even when the weight is a low-confidence fallback (~2.3× inflation, cached).
14. **`app/services/gamification.py:77-84`** `level_up` activity is never emitted; `ACTIVITY_ICONS["level_up"]`
    is dead config / missing feature.
15. **`app/db_init.py:136` vs `:143`** `meal_logged` quest reward mismatch (20 vs 15); first-writer-wins
    makes it order-dependent. Pick one value.
16. **`app/db_init.py:36-68`** schema evolution still has three paths (raw idempotent ALTERs +
    `create_all()` + Alembic). No CI guard that `flask db migrate` yields an empty diff vs models.
17. **`Dockerfile` `--workers 1`** remains load-bearing: `hooks.py:147-159` `_last_rollover_check`
    is per-process in-memory state. Scaling >1 worker silently breaks the 5-min rollover throttle
    and in-memory limiter fallback. Move rollover to cron/CLI + Redis lock before scaling.
