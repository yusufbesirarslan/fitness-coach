## 🔴 CRITICAL

### C1 — `override_macros` meal logging bypasses the physical-sanity clamp ✅ verified
- **File:** `app/blueprints/nutrition/meallog.py:78-98` (`log_meal`, `override_macros` branch)
- **Problem:** When the client supplies `override_macros`, the values pass through `_to_float` +
  `round` and are written **straight to the canonical `MealLog`** — `nutrition_pipeline.clamp_serving_macros`
  is never called. Every other write path clamps: `quick_add_meal` (`diary.py:64`), `diary_log_meal`
  items, menu analyze (`check_serving`/`clamp_to_band`), and the coach commit (`ai_coach.py:435`).
  `clamp_serving_macros`'s own docstring states the UI/diary/menu/coach paths must ALL call it; the
  override branch is the single path that doesn't.
- **Why it's exploitable:** `override_macros` is fully request-controlled. The DB `CheckConstraint`
  (`models.py:210`) only rejects `kalori > 100000`, so a client can POST e.g.
  `override_macros={"kalori": 9999, "protein": 9999, ...}` and persist physically-impossible values.
  This silently corrupts daily totals, the protein nudge, the menu consumed/remaining math, and
  weekly reports — the exact canonical-ledger corruption class prior triages have been closing
  path-by-path (`TRIAGE_FIXES #1`, `TRIAGE_2026-06-23 #1`, `TRIAGE_2026-06-24 #1`). This is the
  next unpatched sibling write path.
- **Fix:** Run `clamp_serving_macros(...)` on the override values (mirror diary.py's
  `_sanitize_meal_macros`) before constructing the `MealLog` entry.

## 🟠 HIGH

### A1 — `_sanitize_menu_text` mojibake table loses ~4 of 12 mappings to duplicate dict keys ✅ verified
- **File:** `app/services/menu_ocr.py:11-17`
- **Problem:** The `replacements` dict has colliding keys after literal evaluation. `'Ä'` is defined
  twice (`→'ğ'` then `→'Ğ'`), `'Å'` twice (`→'ş'` then `→'Ş'`), `'Ã'` three times (`→'Ü'`,`→'Ö'`,`→'Ç'`).
  Later entries overwrite earlier ones, collapsing the table from 12 to ~8 effective entries. The
  lowercase Turkish repairs (`ı` via `Ä±` survives, but `ğ`→only uppercase, `ş`→only uppercase,
  `ü/ö` lowercase variants) are lost.
- **Why it's wrong:** Mojibake repair for Google-Drive/OCR menu text is incomplete and
  order-dependent. Common Turkish lowercase characters won't be repaired, degrading the very
  food-name matching the menu pipeline depends on. (The source byte sequences themselves also look
  mangled — they should be the distinct multi-byte UTF-8 sequences `Ã¼`, `ÅŸ`, `Ã‡`, etc.)
- **Fix:** Use the correctly-distinct mojibake byte sequences as keys, or replace the hand-rolled
  table with a guarded `text.encode('latin-1').decode('utf-8')` round-trip repair.

### A2 — Vision OCR dereferences `resp.choices[0]` without the empty-choices guard ✅ verified
- **File:** `app/services/menu_ocr.py:178` (`_extract_text_from_image`)
- **Problem:** `result = (resp.choices[0].message.content or "").strip()` calls `openai_client`
  directly, not via `_openai_chat`, so it lacks the `if not resp.choices` guard that `ai.py:46`
  exists to provide. A content-filtered image can return empty `choices` → `IndexError`.
- **Why it's wrong:** The surrounding `try/except Exception` swallows the `IndexError` and returns
  `""`, making a content-filter rejection indistinguishable from a genuinely empty menu and bypassing
  the deliberate empty-choices logging in `ai.py`. It would become a hard crash if that try/except
  were ever narrowed.
- **Fix:** Add `if not resp.choices: return ""` before indexing, mirroring `_openai_chat`.

### A3 — `_food_search_static` substring matching returns wrong food (honey → fish) ✅ verified
- **File:** `app/services/fatsecret.py:446` (`_food_search_static`)
- **Problem:** `if q_lower in key or key in q_lower:` — for `q="bal"` (honey) this also matches
  `"balık"` (fish), because `"bal" in "balık"`. Bidirectional substring containment is far too loose
  for short queries.
- **Why it's wrong:** Returns objectively wrong nutrition. Exposure is limited (last-resort fallback
  when FatSecret + LLM are both unavailable), hence High-not-Critical.
- **Fix:** Require token/word-boundary equality, or impose a length floor on the `key in q_lower`
  direction, consistent with the `_food_tokens`/`_is_relevant_food` approach used elsewhere.

### D1 — Legacy ALTER creates `referral_code` as `VARCHAR(12)` vs model/migration `VARCHAR(16)` ⚠ known/re-find
- **File:** `app/db_init.py:55`
- **Problem:** Model (`models.py:57`) + migration `a1b2c3d4e5f6` define `VARCHAR(16)` and
  `generate_referral_code()` produces 16-char codes, but the legacy boot ALTER hardcodes
  `VARCHAR(12)`. On a fresh Postgres DB that hits the legacy ALTER path before `create_all`/Alembic
  widening, inserting a 16-char code would raise `StringDataRightTruncation`.
- **Status:** This is the **same finding as `FIXES.md` S1**. The security agent confirms it is
  reconciled at boot by the Alembic `ALTER COLUMN ... TYPE VARCHAR(16)` on existing DBs, so it is
  **latent, not currently exploitable** — but it remains unfixed in `db_init.py` and is the canonical
  example of the triple-mechanism schema drift (`FIXES.md` S2).
- **Fix:** Change the legacy ALTER to `VARCHAR(16)` or delete it (both `create_all` and the migration
  already own the column).

## 🟡 MEDIUM

### A4 — `quick_add_meal` 500s on non-numeric LLM plan macros
- **File:** `app/blueprints/nutrition/diary.py:55,61,64-69`
- **Problem:** `plan = json.loads(plan_record.plan_data)` then bare `float(meal.get("kalori", 0))`
  with no guard. The plan is LLM-generated and saved verbatim by `save_nutrition_plan` (`plan.py:32`,
  no schema validation). A model emitting `"kalori": "400 kcal"` or a non-list `yemekler` raises and
  returns an unhandled 500. Every other macro entry point uses `_to_float`/`_to_int` precisely to
  avoid this.
- **Fix:** Use `_to_float` for macro extraction, coerce `yemekler` to a list of strings, and validate
  plan structure on save.

### A5 — `_repair_truncated_json` produces invalid JSON on mid-value truncation
- **File:** `app/services/ai_nutrition.py:633-665`
- **Problem:** When LLM batch output is cut mid-numeric-value, the brace-counting + regex repair
  leaves a dangling key/value and `json.loads` still fails — so a whole batch is discarded rather
  than partially recovered. Does not crash (caller catches `JSONDecodeError` → `{}`), hence Medium.
- **Fix:** Track the last complete key/value boundary (as `_salvage_truncated_categories` does) and
  cut there, instead of brace-counting plus regex patching.

### A6 — `calculate_tdee` silently downgrades unknown activity to sedentary
- **File:** `app/services/calculations.py:15-27`
- **Problem:** An unrecognized but non-empty `current_activity` falls through
  `multipliers.get(key, 1.2)` → sedentary, then flows into `target_calories`, the saved
  `UserSession`, and all downstream macro/budget calcs. `MET_CONFIG` and `generate_coach_reply`'s
  `activity_labels` use a *different* vocabulary, increasing drift risk — e.g. `"moderate"` isn't in
  the map (only `sedentary/active/very_active`), so it silently undercounts calories by up to ~30%.
  The code comment itself flags this.
- **Fix:** For a non-empty unrecognized value, reject (400) or map to a documented default and
  surface it, rather than silently treating active inputs as sedentary.

### A7 — `analytics_engine._check_protein_goal` sums by `created_at` instead of canonical `tarih`
- **File:** `analytics_engine.py:98-105`
- **Problem:** Weekly protein is summed with `MealLog.created_at >= week_start_utc`, but the
  canonical nutrition day-key is `MealLog.tarih` (ISO Istanbul) used everywhere else
  (`_today_nutrition_totals`, `analyze_menu`, `query_fitx_metrics`). Mixing naive-UTC insert time
  with an Istanbul week boundary mis-buckets meals near the boundary or backfilled rows. Low impact
  (only gates a congratulatory nudge), but inconsistent with the canonical ledger.
- **Fix:** Sum over `MealLog.tarih >= week_start.isoformat()`.

### D2 — First-supplement XP grant is flush-order dependent; can double-count or skip
- **File:** `app/blueprints/supplements.py:67-72`
- **Problem:** `Supplement.query.filter_by(...).count() == 0` is evaluated **after**
  `db.session.add(supp)`, so autoflush counts the pending row and `first_entry` is almost always
  False; the grant then relies on a post-commit `count() == 1`. Two concurrent adds can both observe
  `count()==1` (double-award) or neither (skip). Unlike the `PumpCheck`/quest grants, there is no
  day-key/unique idempotency guard.
- **Fix:** Compute `first_entry` **before** `db.session.add(supp)`, or gate the one-time bonus on a
  dedicated flag/Activity row so it's deterministic.

### D3 — `reward_dismiss` sets `last_reward_week` from an unordered query
- **File:** `app/blueprints/gamification.py:58-62`
- **Problem:** `WeeklyWinner.query.filter_by(user_id=..., notified=False).all()` has no `ORDER BY`,
  so `rows[0].week_key` is arbitrary. With multiple unseen wins, `last_reward_week` can be set to an
  older week, desyncing the "last seen reward" bookkeeping (`reward_check` deliberately orders by
  `created_at desc, id desc`).
- **Fix:** Order `desc()` and take the newest, or `last_reward_week = max(r.week_key for r in rows)`.

### SEC1 — CSP allows the entire `https://cdn.jsdelivr.net` as a script source
- **File:** `app/hooks.py:41`
- **Problem:** `script-src` permits `'self' 'nonce-…' https://cdn.jsdelivr.net https://*.googletagmanager.com`.
  Allowing any path on jsdelivr (arbitrary npm/GitHub content) partly undercuts the inline-nonce
  hardening: a compromised/typo-squatted asset or an injection pointing `<script src>` at any jsdelivr
  path executes in-origin.
- **Fix:** Pin exact files with Subresource Integrity (`integrity=` + `crossorigin`), self-host the
  few jsdelivr assets, or narrow to specific `cdn.jsdelivr.net/npm/<pkg>@<version>/...` paths.

### SEC2 — `style-src 'unsafe-inline'` / `style-src-attr 'unsafe-inline'` retained
- **File:** `app/hooks.py:53,55`
- **Problem:** Kept as a legacy-browser fallback (acknowledged in comments). Leaves a CSS-injection /
  UI-redress / CSS-exfiltration vector open on older browsers (modern browsers use the stricter
  nonce'd `style-src-elem`). Flagged for completeness as a documented residual.
- **Fix:** Move dynamic widths (progress bars) to CSS custom properties / data-attributes set via
  nonce'd `<style>`, then drop `style-src-attr 'unsafe-inline'`.

## 🟢 LOW

- **D4 — `WorkoutLog` placeholder rows pollute volume aggregation.** `tracking.py:443-447`:
  `complete_workout` writes a synthetic `WorkoutLog(..., volume=0)` so nudges "see" a workout, but
  it's indistinguishable from a real exercise in any volume aggregation. Add a `source` flag, or
  drive the "workout happened today" signal off `PumpCheck` (which has `date_key` + unique guard).
- **D5 — weight parsing only catches `ValueError`.** `tracking.py:44,113,210`: `float(weight)` on a
  JSON list/dict raises uncaught `TypeError` → 500; `if not weight:` also rejects `0`. Catch
  `(ValueError, TypeError)` or route through a `_to_float` validator (other handlers already use
  `_to_int`).
- **D6 — weight-diff message reassigns instead of appending.** `tracking.py:65-73`: the `diff > 0`
  branch reassigns `message`, dropping the "kg kaydedildi" confirmation that the other branches
  append with `+=`. Cosmetic.
- **D7 — `user_metadata` legacy ALTER is `JSONB`-only.** `db_init.py:61`: invalid on SQLite (model
  uses `JSONB().with_variant(JSON(), "sqlite")`). Harmless today (swallowed at debug; `create_all`
  owns the column), but a latent dialect-specific statement. Drop the redundant legacy ALTER.
- **A8 — `food_search` cache read outside the cache lock.** `food.py:28,69` read `_food_id_cache`
  outside `_cache_lock` while `_cache_food_id` mutates it (with eviction) under the lock. Generally
  safe in CPython but inconsistent with the stated locking contract — add a locked accessor or
  document the intent.
- **SEC3 — Cognito ID token signature not verified.** `cognito_idp.py:170-185`: `_decode_claims`
  base64-decodes without `exp`/`iss`/`aud` verification. Acceptable today (token came from Cognito
  over the app's own TLS call, only `sub` is used) but brittle — verify against the pool JWKS for
  defense-in-depth.
- **SEC4 — Logout CSRF bypass when both `Sec-Fetch-Site` and `Referer` are absent.**
  `auth.py:322-332`: `/logout` (GET) allows the request through if both headers are missing. Low
  impact (logout-only nuisance). Fail-closed when both are absent, or move logout to POST.
- **SEC5 — Per-username login limiter enables targeted account-lockout DoS.** `auth.py:45-58,161-162`:
  `login-user:<uname>` caps 15 failures/15 min; an attacker can intentionally exhaust a victim's
  budget. Self-healing/short-window (accepted tradeoff). If a concern, layer in an IP component.
- **SEC6 — Account enumeration via Cognito `UsernameExistsException` on `/register`.**
  `auth.py:92-94,106-109`: a value passing the local pre-check but existing in Cognito surfaces a
  distinct path/response, confirming existence. Rate-limited to 5/hr per IP (substantially mitigated).
- **SEC7 — MCP HTTP transport has no auth (loopback + env opt-in only).** `fitx_mcp/__main__.py`,
  `fitx_mcp/server.py`: tools take `user_id` with no authorization; gated behind
  `FITX_MCP_ALLOW_HTTP=1` + `127.0.0.1`. Correct as designed, but anything reaching `127.0.0.1:8100`
  gets unauthenticated cross-user DB access. Add a shared-secret header even for loopback; never
  publish port 8100.

## False leads ruled out (verified safe this round)

- **MCP SQL injection** — all queries parameterized (psycopg2 `%s`); f-strings only in error
  messages/URLs.
- **S3 IDOR** — `_key_belongs_to` segment-equality enforced on all `expected_user_id` paths;
  avatar URL intentionally public (friends/leaderboard).
- **AI Coach cross-user access** — `user_id` injected server-side from `current_user`;
  `_assert_principal` enforces it. The LLM never supplies `user_id`.
- **SSRF in menu scraper** — DNS-pinned, per-hop revalidation, port allowlist, size caps, manual
  redirect following. Robust.
- **Session fixation / secrets / CSRF** — `session.clear()` on every login; `SECRET_KEY` required;
  FatSecret TLS enforced; no hardcoded creds; two-layer CSRF on all state-changing methods.
- **Ownership/IDOR across reviewed write routes** — `supplement_edit/delete`, `friend_accept/reject`,
  `respond_suggestion`, `chat_*` all verify ownership/friendship before acting.
- **Race conditions** in streak/quest/weekly-reset/pump-check/water/daily-activity/friendship/referral
  — all use `with_for_update` re-check, conditional guarded UPDATE, or DB UNIQUE + `IntegrityError`
  rollback.
- **Migration chain** — linear, single head, no branches.
- **FatSecret token cache / coach pending-action double-confirm** — correctly locked / atomic
  delete-claims with rollback.
